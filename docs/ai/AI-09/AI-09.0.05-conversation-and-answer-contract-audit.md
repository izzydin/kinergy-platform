## 1. Executive Summary

This audit evaluates the contracts, execution flow, persistence mechanisms, message lifecycles, and failure semantics implemented in Milestone AI-08 (`apps/api/src/ai/services/rag/`, `packages/core/src/ai/`). The goal is to verify whether the backend provides the necessary data structures and capabilities required by an enterprise conversational interface (Kynergy Intelligence), and to delineate backend-guaranteed states from frontend client responsibilities.

### Critical Audit Findings

1. **Answer Generation Pipeline:** The core RAG synthesis pipeline is fully implemented, verified, and robust. It executes deterministic application-level abstention, bounded XML context construction, versioned JSON prompting, groundedness verification, and citation cross-checking against authorized retrieved chunks.
2. **Missing Conversation Persistence REST Endpoints:** While domain models (`ConversationSession`), value objects (`ChatMessage`), and an in-memory repository adapter (`InMemoryConversationRepositoryAdapter`) exist, **there are zero REST controllers or endpoints to create, list, retrieve, or delete conversations**.
3. **Session Creation Gap:** In `POST /api/v1/ai/knowledge/query`, if a client passes a non-existent `conversationId`, `ConversationHistoryManagerService` throws `ConversationNotFoundException`, which maps to `404 Not Found`. There is no auto-creation of conversation sessions on query dispatch, and no factory endpoint (`POST /conversations`).
4. **Response DTO Gaps:** The response contract `RAGAnswerResponseDto` exposes only `answer`, `grounded`, `sources`, and `metadata`. It does **not** expose a `conversationId`, a `messageId`, a `timestamp`, chunk text snippets, or token counts (`promptTokens`, `completionTokens`).
5. **Session Loss on Refresh / Restart:** Because conversation sessions are stored in an in-memory `Map` with a 24-hour TTL in the API process, any server restart destroys all active conversations. Furthermore, because no endpoint exists to fetch past messages by `conversationId`, **the frontend cannot reload a conversation from the backend after a browser refresh**.

## 4. Conversation Persistence Model

### 4.1 Persistence Architecture

- **Port:** `IConversationRepositoryPort` (`packages/core/src/ai/ports/outbound/conversation-repository.port.ts`).
  - Methods: `findById(id, tenantId)`, `save(session)`, `delete(id, tenantId)`, `listByUser(tenantId, userId, limit)`.
- **Implementation:** `InMemoryConversationRepositoryAdapter` (`apps/api/src/ai/adapters/conversation/in-memory-conversation-repository.adapter.ts`).
  - Storage: In-memory JavaScript `Map<tenantId, Map<conversationId, ConversationSession>>`.
  - Expiration: Sliding TTL of 24 hours (`session.updatedAt`). Expired sessions are pruned lazily or via `pruneExpiredSessions()`.
  - Database: **Zero Prisma models or SQL tables exist for conversation sessions or messages in PostgreSQL.**

### 4.2 Invariant & Bounding Rules (`ConversationSession`)

Source: `packages/core/src/ai/domain/models/conversation-session.model.ts`

1. **Tenant & User Isolation:**
   - Every session requires non-empty `id`, `tenantId`, and `userId`.
   - `isAuthorized(tenantId, userId, roles)` strictly rejects cross-tenant access. Non-owners are denied unless possessing privileged roles (`ROLE_ADMIN`, `TENANT_ADMIN`, `CLINICAL_SUPERVISOR`).
2. **Turn Alternation & Sanitization:**
   - `addTurn(userText, assistantText)` stores turns in an internal array `_messages: ChatMessage[]`.
   - Automatically sanitizes prompt-injection delimiter tags (`<system>`, `<retrieved_evidence>`, `<evidence_chunk>`, `<instruction>`).
3. **Sliding Memory Cap:**
   - Enforces `MAX_STORED_MESSAGES = 60` (30 complete turns). When exceeded, the oldest turns are silently discarded from memory.
4. **Context Window Token Budgeting:**
   - `selectBoundedHistory()` traverses backwards from the newest turn, stopping when either `maxTurns` (default 10) or `maxTokens` (default 500) is reached.
   - Treats previous assistant turns strictly as non-authoritative conversational context.

### 4.3 The "Browser Refresh" Inability

> [!IMPORTANT]
> **Can the frontend safely reload a conversation after a browser refresh?**  
> **NO.** The frontend cannot reload conversations from the backend for two structural reasons:
>
> 1. There is no controller endpoint to fetch a conversation by ID (`GET /api/v1/ai/conversations/:id` does not exist).
> 2. Even if an endpoint were added, the underlying repository is ephemeral (`InMemoryConversationRepositoryAdapter`); if the NestJS API pod restarts, all session state is lost permanently.

## 6. Consistency, Concurrency & Failure Guarantees

### 6.1 Backend-Enforced Guarantees

1. **Deterministic Abstention (No Hallucination):**
   - If retrieval returns 0 chunks, empty text, or top chunk similarity is below `0.60`, the LLM is **never called**. An immediate, deterministic abstention response is returned.
2. **Citation Verification & Anti-Hallucination:**
   - Candidate citations generated by the LLM are cross-checked against `constructedContext.includedChunks`. Any chunk ID not in the authorized pool is stripped from the response.
3. **Pipeline Deadline Budgeting:**
   - An overall `AbortController` timeout (default `30000ms` = 30s) aborts retrieval and LLM inference if exceeded, throwing `ProviderTimeoutException` (HTTP `504 Gateway Timeout`).
4. **Prompt Injection Neutralization:**
   - Client-provided `system` role messages in `conversationHistory` are stripped. Delimiter tags `<system>`, `<retrieved_evidence>`, `<evidence_chunk>`, and `<instruction>` are escaped to prevent prompt breakouts.

### 6.2 Unhandled Failure & Concurrency Risks

1. **Duplicate Message Submission:**
   - The backend does **not** support idempotency keys (`Idempotency-Key` header or `clientMessageId`). Submitting the same question twice produces two separate retrieval and LLM inference cycles.
2. **Concurrent Request Race Conditions:**
   - If two parallel queries arrive with the same `conversationId`, both will resolve history concurrently and append turns to the in-memory array. The in-memory map has no row-locking or version checks.
3. **Client Disconnection Orphan Inference:**
   - When a user closes the browser tab during a 6-second LLM generation, the HTTP connection drops, but the NestJS request handler continues executing the LLM completion in the background, consuming GPU/CPU resources.
4. **Session Not Found (404) on Fresh ID:**
   - Passing an arbitrary new UUID as `conversationId` fails with `404 Not Found` because the session was never initialized.

## 7. Contract Gaps Matrix (Blockers for Conversational UI)

The following table categorizes all contract gaps between the current AI-08 backend and an enterprise chat interface:

| Contract Gap                              |  Severity  | Description                                                                                                      | Frontend Workaround / Architecture Solution                                                                                                                              |
| :---------------------------------------- | :--------: | :--------------------------------------------------------------------------------------------------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **No Conversation REST Controller**       |  **HIGH**  | No endpoints exist to list, get, create, or delete conversations (`GET /ai/conversations`, etc.).                | The frontend must operate in **Stateless Client-Side History Mode**, persisting conversations in browser `localStorage` and passing `conversationHistory` in each query. |
| **No Auto-Creation of Sessions**          |  **HIGH**  | Passing `conversationId` to `queryKnowledge` throws 404 if the session does not exist in memory.                 | **Omit `conversationId` entirely** from frontend requests until backend conversation creation endpoints are deployed.                                                    |

## 8. Frontend Integration Recommendations: The "Stateless Client History" Pattern

Given the verified backend implementation, **the frontend must adopt a robust Stateless Client-Side History pattern for Phase 1**:

### 8.1 Client-Side State Model

```typescript
interface ClientMessage {
  id: string; // Generated on client via crypto.randomUUID()
  role: 'user' | 'assistant';
  content: string;
  createdAt: string;
  grounded?: boolean;
  sources?: RAGSourceCitationDto[];
  metadata?: RAGMetadataDto;
  status: 'pending' | 'success' | 'error' | 'abstained';
  errorMessage?: string;
}

interface ClientConversation {
  id: string; // Client UUID
  title: string; // Derived from first user query
  createdAt: string;
  updatedAt: string;
  messages: ClientMessage[];
}
```

### 8.2 Safe Query Dispatch Workflow

1. When the user enters a prompt, create a local `ClientMessage` with `role: 'user'` and a placeholder `ClientMessage` with `role: 'assistant', status: 'pending'`.
2. Format the prior messages in the conversation (excluding the current pending turn) into `ChatMessageDto[]` (limiting to the last 10 messages).
3. Dispatch `POST /api/v1/ai/knowledge/query` with:
   ```json
   {
     "query": "User question here",
     "searchMode": "HYBRID",
     "topK": 5,
     "conversationHistory": [
       { "role": "user", "content": "Previous question" },
       { "role": "assistant", "content": "Previous answer" }
     ]
     // NOTE: OMIT conversationId to prevent 404 ConversationNotFoundException
   }
   ```
4. On `200 OK`, update the pending assistant message with `answer`, `grounded`, `sources`, `metadata`, and `status: response.grounded ? 'success' : 'abstained'`.
5. On HTTP error, update the pending assistant message with `status: 'error'` and `errorMessage: error.detail`.
6. Persist the updated `ClientConversation` to browser storage (`localStorage` keyed by `kinergy_chat_conversations_${tenantId}_${userId}`).

## 9. Conclusion & Acceptance Sign-Off

The AI-08 execution pipeline provides a production-grade, highly secure, grounded RAG synthesis engine with verified citations and deterministic abstention. However, **conversation persistence is an internal domain abstraction that is not exposed to HTTP clients**.

By adopting the **Stateless Client-Side History Pattern**, the Kynergy Intelligence frontend can deliver a seamless, high-performance conversational experience immediately, without requiring invasive or speculative backend changes.

- **Contracts Verified Against Code:** Complete.
- **Persistence Guarantees Documented:** In-memory only; no REST endpoints.
- **Contract Gaps & Mitigations Established:** Fully detailed.
