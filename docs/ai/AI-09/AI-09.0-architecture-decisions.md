## ADR-AI-09-01: Client-Side Stateless Conversation Persistence

### Context

Milestone AI-08 introduced domain models for multi-turn sessions (`ConversationSession`) and value objects (`ChatMessage`), backed by an in-memory adapter (`InMemoryConversationRepositoryAdapter`) in `apps/api/src/ai/`. However:

1. No REST controller endpoints exist to create, list, retrieve, or delete conversations (`/api/v1/ai/conversations`).
2. There are zero Prisma models or PostgreSQL tables for conversations; all sessions reside in a volatile process memory `Map` with a 24-hour TTL and vanish upon server restart.
3. If a client transmits a new `conversationId` to `POST /api/v1/ai/knowledge/query`, `ConversationHistoryManagerService` throws `ConversationNotFoundException`, which maps to HTTP `404 Not Found`.

### Decision

For Milestone AI-09, the frontend will adopt a **Stateless Client-Side History Architecture**:

1. Conversational threads will be created, stored, and managed entirely on the client within browser `localStorage`, partitioned strictly by tenant and user (`kinergy_conv_${tenantId}_${userId}`).
2. When querying the backend (`POST /api/v1/ai/knowledge/query`), the client will send recent prior turns in `QueryKnowledgeRequestDto.conversationHistory` (bounded to the last 10 turns) and **omit `conversationId` entirely**.
3. When the backend conversation persistence REST API is implemented in a future milestone, the frontend hook (`useConversationStore`) can be swapped to a remote TanStack Query store without modifying UI components.

### Consequences

- **Positive:**
  - Full persistence across browser refreshes and application restarts without requiring database migrations.
  - Zero server-side 404 errors on session lookup.
  - User can manage multiple conversational threads independently.
- **Negative:**
  - Conversations do not sync across different physical devices or browsers.
  - Storage is capped by browser limits (mitigated by enforcing a 60-message sliding window per thread).

## ADR-AI-09-02: Synchronous JSON Transport with Deferred Fetch-Streaming

### Context

The user experience of generative AI benefits from real-time token streaming. While `OllamaLLMAdapter.generateStream()` implements an asynchronous generator consuming Ollama's stream, `AiRAGController` exposes only a blocking synchronous HTTP `POST` returning a monolithic `RAGAnswerResponseDto`. Furthermore, native browser `EventSource` cannot pass custom `Authorization: Bearer <token>` headers without exposing tokens in URL query strings.

### Decision

1. The frontend will consume standard synchronous HTTP `POST` responses from `POST /api/v1/ai/knowledge/query`.
2. The UI will render deterministic loading skeletons and progressive phase indicators ("Buscando evidencia...", "Sintetizando respuesta...") during the 2.0 to 8.0 second generation window.
3. **Simulating streaming by artificially typing out a completed response is strictly prohibited.**
4. When backend streaming is delivered, the transport will use **authenticated fetch streaming** (`fetch()` + `ReadableStream` reader), preserving Bearer token security.

### Consequences

- **Positive:**
  - Highly robust, atomic request/response lifecycle.
  - Complete error envelope (RFC 7807) available if generation fails.
  - Groundedness, citations, and abstention are evaluated and committed as a single unit.
- **Negative:**
  - Users wait for the full response before reading the first token.

## ADR-AI-09-03: Polling-Based Ingestion Monitoring

### Context

When a user uploads a document to the Knowledge Center, the backend executes an asynchronous 7-stage pipeline (`UPLOADED` -> `VALIDATING` -> `PROCESSING` -> `INDEXING` -> `READY`). The backend does not expose WebSockets or Server-Sent Events for job progress notifications.

### Decision

1. The frontend will implement dynamic interval polling using TanStack Query on `GET /api/v1/ai/knowledge/documents/:id/ingestion`.
2. The polling query will run every 2.0 seconds while the document version's latest job is in an active state (`UPLOADED`, `VALIDATING`, `PROCESSING`, `INDEXING`).
3. Polling terminates immediately when the job enters a terminal state (`READY`, `FAILED`, `CANCELLED`).

### Consequences

- **Positive:**
  - Immediate visual feedback on ingestion transitions without complex socket infrastructure.
  - Reuses existing authenticated HTTP transport and TanStack Query caching.
- **Negative:**
  - Periodic HTTP requests during active processing (negligible overhead for low-concurrency uploads).

## ADR-AI-09-04: Role-Based Intelligence Feature Gating

### Context

The platform's identity module (`packages/core/src/identity`) defines user roles (`UserRole`: `SUPER_ADMIN`, `ADMIN`, `ENERGY_MANAGER`, `OPERATOR`, `COLLABORATOR`), but the `PERMISSIONS` enum currently lacks explicit constants for AI (`ai.chat.query`, `ai.knowledge.manage`). The backend enforces access dynamically via role-to-visibility scope mappings in `RetrievalSecurityPolicyService`.

### Decision

1. The frontend will gate intelligence routes and UI elements based on verified user roles rather than missing permission strings.
2. Route access mapping:
   - `/intelligence/chat`: Accessible to all authenticated staff (`SUPER_ADMIN`, `ADMIN`, `ENERGY_MANAGER`, `OPERATOR`, `COLLABORATOR`).
   - `/intelligence/knowledge`: Restricted to managerial and technical staff (`SUPER_ADMIN`, `ADMIN`, `ENERGY_MANAGER`).
3. Document visibility scopes (`GLOBAL`, `ORGANIZATION`, `DEPARTMENT`, `PRIVATE`) are selected during upload according to the user's role capabilities.

### Consequences

- **Positive:**
  - Immediate alignment with backend security policies without modifying core identity packages.
  - Unauthorized users are barred at the routing layer before making backend requests.
- **Negative:**
  - Custom permissions cannot be configured per user without future identity enum expansion.

## ADR-AI-09-05: Authoritative Citation Metadata & Snippet Separation

### Context

Source citations generated by the RAG pipeline are validated against PostgreSQL evidence chunks to prevent hallucination. `RAGSourceCitationDto` exposes `documentId`, `documentTitle`, `chunkId`, `pageNumber`, `headingPath`, `relevanceScore`, and `sourceStrategy`. However, it intentionally omits the full text snippet (`content`) of the chunk to minimize transport payload size. Furthermore, no endpoint exists to fetch an individual chunk by ID (`/api/v1/ai/knowledge/chunks/:chunkId`).

### Decision

1. Citation badges in the chat interface will present authoritative metadata (`documentTitle`, `pageNumber`, `headingPath`) directly from the verified DTO.
2. Clicking a citation badge will open a document drawer showing document details and offering a direct download link (`GET /api/v1/ai/knowledge/documents/:documentId/content`).
3. In-line chunk snippet modal previews are deferred until a dedicated backend chunk REST endpoint is implemented.

### Consequences

- **Positive:**
  - Lean network payloads for chat queries.
  - Zero hallucination of source metadata.
  - Direct access to original source documents.
- **Negative:**
  - Users must view the original document rather than a cropped text snippet modal.
