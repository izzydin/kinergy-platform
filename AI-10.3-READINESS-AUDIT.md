# AI-10.3-01 — Secure Document Upload and Processing Readiness Audit

**Milestone:** AI-10.3-01  
**Readiness Verdict:** **READY WITH RISKS**  
**Date:** November 27, 2026  
**Roles:** Principal Application Security Architect & Senior Backend Engineer  
**Scope:** Verification-first security audit of Kynergy's document upload entry points, content validation, object storage adapters, parser isolation, malware defenses, and RAG ingestion lifecycle.

---

## Executive Summary & Verdict

### Readiness Verdict:

> ### **READY WITH RISKS**
>
> _The core document upload and ingestion infrastructure features strong static validation (magic byte sniffing, SHA-256 deduplication, DOCX ZIP bomb bounds, path traversal sanitization, and fail-closed tenant scoping). However, significant security gaps exist around antivirus/malware scanning (completely missing), parser memory/timeout execution bounds during async worker processing, and in-memory buffering under Multer._

### Key Architecture Strengths (Verified):

1. **Authenticated & Authorized Ingress:** Every upload requires JWT authentication (`AuthenticationGuard`, `AuthorizationGuard`) and explicit permission `ai.documents.upload`.
2. **Deep Content Sniffing:** `DocumentContentValidatorService` validates magic bytes independently of file extensions, enforces strict UTF-8 control byte checks, blocks active JavaScript/Launch actions in PDFs, and restricts DOCX compression ratios (100:1 max) and entry counts (1000 max) against ZIP bombs.
3. **Partitioned Storage Architecture:** All uploaded files are stored under partition-isolated paths (`tenants/{tenantId}/knowledge_base/...`) using sanitized basenames (`StorageKeyUtil.sanitizeFilename`), completely neutralizing path traversal (`../`) and symlink attacks.
4. **Authoritative Publication Lifecycle:** Documents enter the database in `UPLOADED` state. Chunks and embeddings are not queryable until the ingestion job successfully completes and transitions to `READY`. Soft-deleted or unvalidated documents fail closed in all retrieval queries.

### Critical Gaps Requiring AI-10.3 Implementation:

1. **Absence of Antivirus / Malware Scanning (`KY-UPL-001` - HIGH):** There is currently zero dynamic antivirus or malware scanning (ClamAV, VirusTotal, or cloud scanning sidecar) before files are persisted to object storage.
2. **In-Memory Buffering Under Multer (`KY-UPL-002` - MEDIUM):** `FileInterceptor('file')` uses default memory storage. Concurrent multipart uploads of 10MB files directly consume Node.js heap, creating a potential Denial of Service (DoS) attack surface under high concurrency.
3. **Parser Process Isolation (`KY-UPL-003` - MEDIUM):** Parsers (`unpdf`, `mammoth`, `marked`) execute within the main API / Node.js worker process. While they are pure JavaScript/TypeScript (no native C binaries or shell execution), CPU-intensive regex or memory allocations could stall the event loop.

## 1. Upload Entry Points & Ingress Security

### 1.1 Endpoint Inventory

| Endpoint                                      | HTTP Method | Auth Guard                                  | Permission Required   | Input Format          | Handler / Service                                                        |
| :-------------------------------------------- | :---------- | :------------------------------------------ | :-------------------- | :-------------------- | :----------------------------------------------------------------------- |
| `/api/v1/ai/knowledge/documents`              | `POST`      | `AuthenticationGuard`, `AuthorizationGuard` | `ai.documents.upload` | `multipart/form-data` | `AiDocumentController.uploadDocument` -> `SecureDocumentUploadService`   |
| `/api/v1/ai/knowledge/documents/:id/versions` | `POST`      | `AuthenticationGuard`, `AuthorizationGuard` | `ai.documents.upload` | `multipart/form-data` | `AiDocumentController.uploadNewVersion` -> `SecureDocumentUploadService` |
| `/api/v1/ai/documents` (Alias)                | `POST`      | `AuthenticationGuard`, `AuthorizationGuard` | `ai.documents.upload` | `multipart/form-data` | Alias to above                                                           |

### 1.2 Authentication & Tenant Identity Derivation

- **Authoritative Identity:** Tenant identity is resolved strictly from `@CurrentUser() user: AuthenticatedUserPayload`. Client-supplied request body `tenantId` is forbidden or overwritten.
- **Missing Tenant Handling:** If `user.tenantId` is missing or empty, `UnauthorizedDocumentAccessException` is thrown immediately (HTTP 401/403).
- **Two-Phase Upload Workflow:**
  - _Phase 1:_ Upload bytes to object storage under tenant-isolated key.
  - _Phase 2:_ Atomically insert `KnowledgeDocument`, `DocumentVersion`, and `IngestionJob` into PostgreSQL.
  - _Compensating Cleanup:_ If database persistence fails in Phase 2, storage deletion is immediately triggered to prevent orphaned files.

### 1.3 Upload Library & Buffering Behavior

- **Library:** `@nestjs/platform-express` with default `FileInterceptor('file')` (Multer memory storage).
- **Buffer Flow:** Entire file contents are loaded into `file.buffer: Buffer` in Node.js RAM before reaching `SecureDocumentUploadService`.
- **Size Limits:** Configured via `AiConfiguration.maxDocumentSizeBytes` (default: 10 MB, 10,485,760 bytes). Files exceeding this limit are rejected by `DocumentSizeLimitExceededException` (HTTP 400).
- **Concurrency Risk:** 100 concurrent uploads of 10 MB files would consume ~1.0 GB of Node.js heap memory simultaneously.

## 2. File Validation Pipeline Analysis

`DocumentContentValidatorService` executes a multi-step static inspection pipeline before any file is saved or parsed:

```
[Raw Multipart Buffer]
       │
       ▼
1. Size & Non-Empty Check ───────► Rejects 0-byte or >10MB files (DocumentSizeLimitExceededException)
       │
       ▼
2. Extension & Basename Check ──► Sanitizes filename; rejects missing or illegal extensions
       │
       ▼
3. Content Sniffing (Magic Bytes)
       ├─ %PDF- (0x25 0x50 0x44 0x46 0x2d) ────────► PDF
       ├─ PK\x03\x04 (0x50 0x4b 0x03 0x04) ────────► DOCX (OpenXML)
       ├─ Valid UTF-8, no nulls (0x00) ────────────► TXT / MARKDOWN
       └─ Known binary (PNG, JPEG, ELF, MZ/EXE) ───► REJECTED (UnsupportedDocumentFormatException)
       │
       ▼
4. Format Deep Structural Validation
       ├─ PDF: Checks %%EOF trailer; BLOCKS /Launch and /JavaScript execution vectors
       ├─ DOCX: Parses Central Directory; enforces ZIP bomb limits:
       │         - Max uncompressed size: 50 MB
       │         - Max entry count: 1,000 entries
       │         - Max compression ratio: 100:1
       │         - Verifies [Content_Types].xml and word/document.xml
       └─ TXT/MD: Strict UTF-8 decoding; blocks control bytes < 32 (except \t, \n, \r)
       │
       ▼
5. Consistency Check ────────────► Asserts extension matches detected format & declared MIME matches detected format
       │
       ▼
6. SHA-256 Checksum ─────────────► Computes SHA-256 digest; rejects intra-document duplicate versions
```

### Classification of Validation Coverage:

- **Allowed Extensions:** `.pdf`, `.docx`, `.txt`, `.md`, `.markdown` (**VERIFIED**).
- **MIME Spoofing Defense:** Magic bytes take precedence over client-declared MIME and extension (**VERIFIED**).
- **Polyglot & Binary Embeddings:** Executables (`MZ`, `ELF`) and images disguised as text are rejected (**VERIFIED**).
- **PDF Active Content:** `/Launch` and `/JavaScript` actions are statically detected and blocked (**VERIFIED**).
- **ZIP Bombs:** Nested decompression ratio and entry count caps prevent decompression bombs (**VERIFIED**).

## 3. Storage and Temporary File Architecture

### 3.1 Storage Adapters

1. **`LocalStorageAdapter` (Dev/Test):** Writes files to disk under `${STORAGE_LOCAL_ROOT}/tenants/{tenantId}/knowledge_base/...`.
2. **`S3StorageAdapter` (Staging/Production):** Stores objects in AWS S3 / MinIO compatible object storage.

### 3.2 Key Generation & Path Traversal Defense

- Keys are generated via `StorageKeyUtil.generateObjectKey`:
  ```
  tenants/{tenantId}/knowledge_base/{year}/{month}/{uniqueId}-{sanitizedFilename}
  ```
- `StorageKeyUtil.sanitizeFilename` strips all path traversal tokens (`../`, `..\\`), replaces non-alphanumeric characters with underscores, and prevents hidden files.
- `StorageKeyUtil.assertTenantOwnsKey(tenantId, key)` verifies that the key prefix strictly matches `tenants/{tenantId}/`.

### 3.3 Public Access & Download Authorization

- Storage buckets and local directories have **zero public HTTP access**.
- File downloads and previews are strictly authenticated:
  1. User requests a temporary token via `POST /api/v1/ai/knowledge/documents/:id/preview-token`.
  2. `PreviewTokenService` generates an HMAC-SHA256 signed token binding `(tenantId, userId, documentId, versionId, exp)`.
  3. User downloads content via `GET /api/v1/ai/knowledge/documents/:id/download?token=...` or signed S3 presigned URL (15-minute expiry).
  4. Raw internal storage keys (`storageKey`) are filtered out of all API response DTOs (`DocumentDetailResponseDto`, `DocumentVersionResponseDto`).

## 4. Malware, Antivirus, and Sandbox Defenses

### 4.1 Current Antivirus Posture: MISSING

- **Evidence:** Code inspection across the monorepo confirms **zero integration with ClamAV, AWS GuardDuty Malware Protection, or external ICAP scanners**.
- **Assessment:** While `DocumentContentValidatorService` provides comprehensive static format inspection, it does not scan for known virus signatures, macro payloads inside DOCX VBA streams, or weaponized PDF exploit chains.
- **Risk Level:** **HIGH** for production deployments where untrusted external documents might be uploaded by clinic staff.

### 4.2 Archive Handling & Decompression

- Direct archive uploads (`.zip`, `.tar.gz`, `.7z`) are **unsupported and rejected**.
- DOCX files are internally ZIP archives. DOCX ZIP extraction is handled safely with strict entry limits (1,000 entries, 50MB uncompressed, 100:1 ratio). Path traversal in DOCX entry names is mitigated because entries are processed in-memory without extracting to disk.

## 5. Document Parsing and Extraction Security

### 5.1 Format & Parser Inventory

| Format         | Parser Adapter           | Underwriting Library          | Native Binaries / Subprocesses | External Network / SSRF Risks                 |
| :------------- | :----------------------- | :---------------------------- | :----------------------------- | :-------------------------------------------- |
| **PDF**        | `PdfParserAdapter`       | `unpdf` (pure JS PDF.js fork) | None (Pure JS)                 | None (Disabled external font/image fetching)  |
| **DOCX**       | `DocxParserAdapter`      | `mammoth` (^1.13.0)           | None (Pure JS)                 | None (Ignores external XML entity references) |
| **Markdown**   | `MarkdownParserAdapter`  | `marked` (AST Lexer)          | None (Pure JS)                 | None (Lexer only; HTML rendering disabled)    |
| **Plain Text** | `PlainTextParserAdapter` | Native `TextDecoder`          | None                           | None                                          |

### 5.2 Parser Execution Model & Sandboxing

- **Execution Context:** Parsers execute in-process within Node.js.
- **Privilege Sharing:** Parsers run under the same OS user and process permissions as the API server or background worker.
- **Timeouts & Resource Limits:** Parsers accept `timeoutMs` (default: 30s) and `maxSizeBytes` (default: 10MB).
- **Subprocess Isolation:** Currently **no separate sandboxed worker container** exists for parsing. A parser crash (e.g. out-of-memory error on pathological PDF) affects the worker thread.

## 6. Ingestion Lifecycle & Publication Safeguards

### 6.1 Publication Invariants

- A newly uploaded document is assigned `IngestionStatus.UPLOADED`.
- It moves sequentially: `UPLOADED` -> `VALIDATING` -> `PROCESSING` -> `INDEXING` -> `READY`.
- **Zero Premature Retrieval:** Semantic search queries explicitly filter on:
  ```sql
  WHERE ig."status" = 'ACTIVE' AND kd."deleted_at" IS NULL
  ```
  Chunks are only indexed into `ACTIVE` generations, and queries join against `knowledge_documents.status` and `deleted_at`, guaranteeing that documents in `UPLOADED`, `PROCESSING`, or `FAILED` states are invisible to retrieval.

## 8. Recommended Implementation Sequence for AI-10.3

1. **AI-10.3-02 — Antivirus and Malware Scanning Integration (`KY-UPL-001`):**
   - Introduce an asynchronous or inline malware scanning port (`IMalwareScannerPort`) with ClamAV / Mock adapter.
   - Quarantine files that fail malware checks and prevent pipeline execution.
2. **AI-10.3-03 — Multer Stream Hardening & Temporary File Lifecycle (`KY-UPL-002`):**
   - Configure disk-backed temporary storage or streaming limits to prevent heap exhaustion during large concurrent uploads.
   - Implement deterministic temporary file cleanup with strict error-handling hooks.
3. **AI-10.3-04 — Parser Resource Bounds & Timeout Hardening (`KY-UPL-003`):**
   - Enforce memory caps, abort controllers, and isolated worker boundaries for complex PDF and DOCX parsing.
4. **AI-10.3-05 — End-to-End Adversarial Upload Test Suite:**
   - Verify rejection of EICAR test strings, corrupt PDFs, polyglot executables, and pathological decompression bombs.
