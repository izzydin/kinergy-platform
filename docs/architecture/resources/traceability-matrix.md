# Phase 6: Resources Management — Requirement-to-Test Traceability Matrix

## 1. Executive Summary & Traceability Architecture

This matrix provides the canonical, end-to-end verification baseline for **Phase 6: Resources Management**. It proves that every business requirement is deterministically enforced across the six-tier architecture:

$$\text{Business Requirement} \longrightarrow \text{Domain Rule} \longrightarrow \text{Use Case / Handler} \longrightarrow \text{HTTP API} \longrightarrow \text{Frontend Feature} \longrightarrow \text{Automated Test}$$

Every cell references the actual, verified source file, class name, endpoint, component, or test suite in the Kinergy Platform monorepo. No speculative or artificial layers have been introduced.

## 3. Explicit Architecture Gaps & "N/A" Justification Matrix

In strict compliance with Kinergy's zero-speculation policy, certain architectural layers are intentionally not implemented. The table below documents these decisions:

| Feature / Concept                                | Layer                | Status                                  | Authoritative Architectural Justification                                                                                                                                                             |
| :----------------------------------------------- | :------------------- | :-------------------------------------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Direct Client Foreign Keys**                   | Domain & Persistence | **N/A — Decoupled by Design**           | Resources are owned by the facility, not individual clients. Transactions reference clients via unconstrained scalar string `referenceId`. Prevents GDPR deletion cascades.                           |
| **Relational Room Foreign Keys**                 | Domain & Persistence | **N/A — Deferred by Business Model**    | Equipment is an amenity inside physical spaces, not an independently bookable calendar line. Modeled as informational `AssetLocation` Value Object to prevent appointment disruptions during repairs. |
| **Sales Module Direct DB Access**                | Persistence          | **N/A — Prohibited by Invariant**       | Inventory owns all stock mutation rules. Commercial modules must never execute direct SQL updates on inventory tables; integration is strictly routed through `InventoryStockDecrementPort`.          |
| **Distributed 2-Phase Commit (2PC)**             | Application          | **N/A — Rejected for Scalability**      | Monorepo operates with local ACID transactions per bounded context. Cross-domain workflows use local orchestration and compensating transactions.                                                     |
| **Pessimistic Read Locks (`SELECT FOR UPDATE`)** | Persistence          | **N/A — Rejected to Prevent Deadlocks** | System uses Optimistic Concurrency Control (OCC) with integer `version` counters. Readers never block writers, eliminating distributed lock contention.                                               |
| **Full Event Sourcing Engine**                   | Architecture         | **N/A — Non-Goal**                      | Aggregate state is maintained in normalized relational tables. History ledgers serve an audit and regulatory compliance role, not state reconstruction.                                               |
