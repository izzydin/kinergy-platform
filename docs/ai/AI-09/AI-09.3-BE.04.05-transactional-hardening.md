## 1. Executive Summary

This report documents the architectural review, transactional failure hardening, bounded retry policy implementation, and real PostgreSQL concurrency verification for all BE.04 application workflows.

Key achievements:

1. **Transaction Boundary Integrity:** Verified that all child aggregate writes (`AiConversation`, `AiConversationTurn`, `AiConversationMessage`, `AiConversationAuditLog`) in both `CreateConversationWithInitialTurnUseCase` and `ReserveConversationTurnUseCase` execute within a single atomic PostgreSQL transaction boundary using `IAiConversationTransactionRunner`.
2. **Atomic Rollback Guarantee:** Verified that transaction aborts or errors at any phase roll back the entire transaction completely with zero partial writes and zero orphaned database records.
3. **Bounded Transient Retry Policy:** Implemented automatic bounded retries with jittered exponential backoff for known transient database failures (write conflicts `P2034`, deadlocks `40P01`, serialization failures `40001`, connection drops `P1017`) in `PrismaAiConversationTransactionRunner`. Deterministic domain errors, unique constraint collisions, and validation failures are strictly excluded from retries.
4. **Authoritative Concurrency Arbitration:** Verified concurrent requests using independent PostgreSQL connections:
   - Same-key concurrent creation/reservation: exactly 1 request wins (`CREATED`), while the competing request waits for commit, verifies the SHA-256 payload hash, and returns `EXISTING_RECOVERED` with 1 single turn in PostgreSQL.
   - Competing different-turn reservation on the same conversation: exactly 1 request wins, while the other is rejected with `TurnAlreadyInProgressError` enforced authoritatively by PostgreSQL partial unique index `ai_conversation_active_generation_idx`. Zero orphan user messages are persisted.
5. **Observability & Privacy-Safe Redaction:** Defined `IAiConversationLoggerPort` and `AiConversationRedactionService` ensuring that operational identifiers (`operation`, `tenantId`, `userId`, `conversationId`, `turnId`, `clientTurnId`, `idempotencyOutcome`) are captured while sensitive fields (`prompt`, `userPrompt`, `content`, `tokens`, `passwords`) are strictly redacted.

| :--------------------------------- | :------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------ |
| **Mid-Flight Abort**               | Exception thrown after conversation write before turn creation | Transaction rolls back completely; throws `TransactionFailureError`                                                  | **0 rows** in `ai_conversations`, `ai_conversation_turns`, `ai_conversation_messages` |
| **Invalid Foreign Key**            | Turn reservation referencing non-existent `conversationId`     | Foreign key check fails; throws typed persistence exception                                                          | Transaction aborted; zero orphan turns created                                        |

| **Concurrent Active Generation**   | Two distinct turns racing for active slot on same conversation | One commits; second hits `ai_conversation_active_generation_idx`; rolls back and throws `TurnAlreadyInProgressError` | Exactly 1 turn committed; zero orphan user messages                                   |

## 4. Retry Policy

### 4.1 Transient vs. Non-Transient Classification

The transient retry policy in `PrismaAiConversationTransactionRunner` strictly distinguishes between transient infrastructure aborts and deterministic application errors:

```typescript
export function isTransientDatabaseError(error: unknown): boolean {
  if (!error) return false;

  if (error instanceof Prisma.PrismaClientKnownRequestError) {
    if (error.code === 'P2034') return true; // Write conflict / deadlock
    if (error.code === 'P1017') return true; // Server closed connection
    if (error.code === 'P2024') return true; // Connection pool timeout
  }

  const msg = error instanceof Error ? error.message.toLowerCase() : String(error).toLowerCase();
  return (
    msg.includes('40001') || // serialization_failure
    msg.includes('could not serialize access') ||
    msg.includes('40p01') || // deadlock_detected
    msg.includes('deadlock detected') ||
    msg.includes('p2034') ||
    msg.includes('connection terminated') ||
    msg.includes('connection closed') ||
    msg.includes('server has closed the connection')
  );
}
```

### 4.2 Retry Constraints & Guarantees

- **Bounded Attempts:** Maximum 2 retries (3 total attempts).
- **Jittered Exponential Backoff:** `delay = 50ms * 2^(attempt - 1) + jitter(0..30ms)`.
- **Preserved Non-Retryables:** The following are **NEVER** retried:
  - Domain application errors (`AiConversationApplicationError`).
  - Validation errors (`InvalidTurnInputError`).
  - Ownership violations (`InvalidOwnershipException`, `TenantOwnershipViolationError`).
  - Unique constraint violations (`P2002`, `23505`).
  - Foreign key violations (`P2003`, `23503`).

## 5. Idempotency Behavior & Concurrency Methodology

### 5.1 Same-Key Concurrency Arbitration

When two concurrent requests arrive simultaneously with the identical `clientTurnId`:

1. Both requests attempt to insert into `ai_conversation_turns`.
2. PostgreSQL's composite unique constraint `uq_turn_tenant_client_turn_id` guarantees that exactly one transaction succeeds.
3. The losing transaction receives a unique constraint violation and rolls back completely.
4. The application catches the collision in `isIdempotencyConflict()`, waits for the winning transaction's commit to become visible, retrieves the committed turn, verifies the payload hash:
   - If payload matches: returns `EXISTING_RECOVERED` with `isIdempotentReplay: true`.
   - If payload differs: throws `DuplicateClientTurnPayloadMismatchError`.
5. PostgreSQL state: Exactly **1 turn** and **2 messages** exist.

### 5.2 Independent Multi-Connection Concurrency Testing

Verification tests in `transactional-consistency.integration.spec.ts` use two independent `PrismaClient` instances (`primaryPrisma` and `secondaryPrisma`) with separate PostgreSQL connection pools executed concurrently via `Promise.all` and `Promise.allSettled`.
