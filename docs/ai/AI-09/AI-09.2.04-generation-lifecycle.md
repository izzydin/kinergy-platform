# AI-09.2.04 — Message Submission & Generation Lifecycle

## Role & Executive Summary

**Role**: Principal React Engineer and Senior Application Architect.  
**Milestone**: AI-09.2.04 — Message Submission & Generation Lifecycle.

This milestone establishes a resilient, deterministic, and typed request lifecycle for conversational prompt submission in the Kynergy Intelligence assistant. Without prematurely introducing streaming, it implements an explicit finite state machine (FSM), strict duplicate submission prevention via submission mutex locks, multi-turn history bounded context building, request cancellation via `AbortController`, stale response protection during thread switching, and guaranteed prompt draft preservation upon submission failure.

---

## 1. Generation State Machine Architecture

The generation state machine is decoupled from presentational concerns and governed by a pure reducer with strict transition validity checks.

### Presentation & Operational States

```
       ┌───────────────────────────────┐
       │             IDLE              │◄─────────────────────────────┐
       └──────────────┬────────────────┘                              │
                      │ SUBMIT                                        │
                      ▼                                               │
       ┌───────────────────────────────┐                              │
       │            PENDING            ├──────────────┐               │
       └──────┬───────────────┬────────┘              │               │
STREAM_START  │               │ COMPLETE (standard)   │ FAIL / CANCEL │
              ▼               ▼                       ▼               │
       ┌─────────────┐ ┌─────────────┐         ┌─────────────┐        │
       │  STREAMING  │ │  COMPLETED  │         │   FAILED    │        │
       └──────┬──────┘ └──────┬──────┘         └──────┬──────┘        │
              │               │                       │               │
       ┌──────┴──────┐        │                       │               │
       │ CANCEL /    │        │                       │               │
       │ INTERRUPT   │        │                       │               │
       ▼             ▼        │                       │               │
 ┌───────────┐ ┌───────────┐  │                       │               │
 │ CANCELLED │ │INTERRUPTED│  │                       │               │
 └─────┬─────┘ └─────┬─────┘  │                       │               │
       │             │        │                       │               │
       └─────────────┴────────┴───────────────────────┴───────────────┘
                                   RESET / NEW TURN
```

### Transition Validity Matrix

| Source State      | Permitted Destination States                      | Description                                                                  |
| :---------------- | :------------------------------------------------ | :--------------------------------------------------------------------------- |
| **`IDLE`**        | `PENDING`                                         | Initial prompt submission initiated.                                         |
| **`PENDING`**     | `STREAMING`, `COMPLETED`, `FAILED`, `CANCELLED`   | Standard HTTP completion, start of SSE stream, failure, or user abort.       |
| **`STREAMING`**   | `COMPLETED`, `INTERRUPTED`, `CANCELLED`, `FAILED` | Incremental tokens finish, connection drops, user cancels, or stream errors. |
| **`COMPLETED`**   | `IDLE`, `PENDING`                                 | Finished turn returns to idle or accepts immediate next submission.          |
| **`FAILED`**      | `IDLE`, `PENDING`                                 | Error displayed; composer retains draft, ready for retry or reset.           |
| **`CANCELLED`**   | `IDLE`, `PENDING`                                 | In-flight request aborted by user action or view teardown.                   |
| **`INTERRUPTED`** | `IDLE`, `PENDING`                                 | Incomplete generation preserved with diagnostic marker.                      |

Illegal transitions (e.g., `IDLE` → `COMPLETED` or `FAILED` → `STREAMING`) are rejected deterministically by `isValidGenerationTransition()`, preventing silent state corruption.

## 2. Message Submission Lifecycle

When a practitioner sends a prompt from `ChatComposer`, the execution adheres to the following sequential stages:

```
[User Submits Prompt]
         │
         ▼
 1. Draft Validation (length: 3..1000 characters)
         │
         ▼
 2. Submission Mutex Lock Check (rejects concurrent / rapid repeated submissions)
         │
         ▼
 3. Conversation Provisioning (creates thread if in uninitialized '/intelligence/chat')
         │
         ▼
 4. Stable Identifiers (crypto.randomUUID() for userMessageId and assistantMessageId)
         │
         ▼
 5. Dispatch 'SUBMIT' -> FSM status moves to PENDING
         │
         ▼
 6. Optimistic Storage & Cache Commitment
    - User message (status: 'success')
    - Assistant placeholder (status: 'pending')
    - TanStack Query cache updated immediately
         │
         ▼
 7. Bounded Context Construction (up to 10 completed historical turns, excluding pending turn)
         │
         ▼
 8. Backend API Execution (assistantApi.queryKnowledge with AbortSignal)
         │
    ┌────┴──────────────────────────┐
    ▼                               ▼
[Success]                        [Failure / Abort]
 9a. Reconcile with Canonical     9b. Reconcile Failed Turn
     Answer, Sources, Telemetry       - status: 'error'
     - status: 'success'              - error: normalized message
     - FSM -> COMPLETED               - FSM -> FAILED or CANCELLED
     - Query caches updated           - Re-throw error to retain draft in Composer
```

## 3. Duplicate Submission Prevention Strategy

To eliminate double posts, race conditions, and accidental repeated clicks:

1. **Submission Mutex Lock (`isSubmittingMutexRef`)**:
   - An imperative `useRef` lock is engaged synchronously before any async operations begin.
   - Any secondary calls while a request is in flight (`isSubmittingMutexRef.current === true` or `status === 'PENDING'`) return immediately without side effects.
2. **Keyboard Shortcut Debouncing**:
   - `ChatComposer` disables the submit button and ignores repeated `Enter` / `Ctrl+Enter` key events while `isSubmitting` is active.
3. **Optimistic Turn Deduplication**:
   - User messages receive pre-assigned deterministic UUIDs (`userMessageId`), preventing optimistic turn clobbering.
4. **Stale Response Protection**:
   - The hook continuously tracks `currentConversationIdRef`. If a practitioner switches threads while an LLM query is in-flight, the completed response reconciles into the target thread's partitioned storage without contaminating the newly selected view.
5. **AbortController Management**:
   - Each submission initializes an isolated `AbortController`.
   - If the component unmounts or `cancelGeneration()` is triggered, `controller.abort()` cancels the network operation immediately.

## 4. Frontend State Ownership Model

To eliminate state duplication and race conditions across multiple stores:

| State Domain                 | Owner                    | Storage Layer                                                                 | Lifecycle                                                    |
| :--------------------------- | :----------------------- | :---------------------------------------------------------------------------- | :----------------------------------------------------------- |
| **Persisted Thread History** | Server / Browser Storage | `assistantStorageService` (Partitioned `localStorage`) + TanStack Query cache | Long-lived, authoritative across tabs.                       |
| **Active Query Cache**       | TanStack Query           | Query keys: `aiAssistantKeys.conversation(...)`                               | Reactive cache synchronized with storage.                    |
| **Generation Lifecycle**     | `useGenerationLifecycle` | Local FSM (`useReducer`) + `useRef` locks                                     | Transient, scoped to active submission.                      |
| **Input Draft**              | `ChatComposer`           | Component `useState`                                                          | Local; preserved across failures until acknowledged success. |
| **Stream Buffer (Future)**   | `useGenerationLifecycle` | Transient buffer                                                              | Temporary accumulator until final turn reconciliation.       |

## 5. Error Taxonomy & Draft Preservation

The lifecycle classifies errors into standardized categories using `normalizeApiError`:

- **Validation Errors (400)**: Prompt length violations (< 3 or > 1,000 characters) rejected before network dispatch.
- **Unauthorized / Forbidden (401/403)**: Session expiration or missing permissions.
- **Rate Limiting (429)**: Backend inference quota exhausted.
- **Backend / Inference Failures (500/502/503)**: Local Ollama or Pinecone engine unreachable.
- **Network / Offline**: Connection drop during transport.
- **User Abort / Cancel**: Operation terminated via `AbortController`.

### Draft Preservation Guarantee

When `submitMessage` encounters an error:

1. The assistant message turn in storage is updated with `status: 'error'` and the diagnostic error message.
2. The state machine transitions to `FAILED`.
3. The error is re-thrown to the caller (`handleSendMessage` in `ChatWorkspace`).
4. `ChatComposer.handleSubmit` intercepts the error and **does not clear** `setDraft('')`.
5. The practitioner's query remains intact in the textarea for review, editing, or retry.

## 7. Known Limitations & Streaming Readiness

1. **Idempotency Keys**: The current AI-08 backend (`POST /api/v1/ai/knowledge/query`) does not support client-generated `Idempotency-Key` headers. Deduplication is enforced at the frontend transport and mutex layer.
2. **Streaming Integration (AI-09.2.05)**:
   - The `STREAMING` status and transitions (`PENDING` → `STREAMING` → `COMPLETED` / `INTERRUPTED`) are defined and validated in the state machine.
   - Milestone AI-09.2.05 can seamlessly plug Server-Sent Events (`EventSource` or `fetch` stream reader) into `useGenerationLifecycle` by emitting `STREAM_START` and incrementally appending tokens into the pending assistant turn.
