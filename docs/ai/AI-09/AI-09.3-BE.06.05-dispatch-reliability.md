## 1. Executive Summary

Milestone **BE.06.05** establishes the reliable execution and lifecycle control bridge between canonical conversation turn reservation (AI-09.3) and the RAG generation pipeline (AI-08).

### Core Architectural Guarantees

1. **Durable Work via PostgreSQL Commit**:
   - Turn reservation (`CreateConversationWithInitialTurnUseCase`, `ReserveConversationTurnUseCase`) commits the turn with `status: PENDING`, user message, and assistant placeholder within an atomic transaction.
   - Work is durably persisted prior to dispatch. Process crashes or network drops cannot lose work because pending turns are recovered from PostgreSQL.
2. **Immediate Non-Blocking Dispatch**:
   - On successful turn reservation (`!isIdempotentReplay`), `IAiTurnDispatcherPort.dispatchTurn` is invoked.
   - Execution runs asynchronously in the background via detached tasks (`setImmediate`), allowing HTTP turn reservation controllers to return immediately (HTTP 201 Created).
   - REST controllers never execute RAG retrieval or LLM inference.
3. **Idempotent Retry Filtering**:
   - Replays with existing `clientTurnId` return `isIdempotentReplay: true` and never trigger duplicate dispatches, duplicate LLM calls, or duplicate message rows.
4. **Resilient Background Polling & Stalled Turn Recovery**:
   - `AiTurnGenerationWorker` periodically polls for unexecuted `PENDING` turns and `STREAMING` turns whose leases expired.
   - Dispatches recovered turns with zero duplicate work by checking the dispatcher's active registry.
5. **Graceful Worker Shutdown**:
   - `AiTurnGenerationWorker` implements `OnApplicationShutdown`.
   - Halts polling, drains in-flight active turns within a configured timeout budget (e.g. 5,000ms), and signals remaining in-flight tasks with `WORKER_SHUTDOWN` if the budget elapses.
6. **Cancellation & In-Flight Abort Signaling**:
   - `CancelConversationTurnUseCase` atomically transitions turn and assistant attempt statuses to `CANCELLED` in PostgreSQL and updates conversation `lastActivityAt`.
   - Signals active worker execution via `IAiTurnDispatcherPort.cancelTurn` using `AbortController.abort()`.
   - Replaying cancellation is strictly idempotent (`isAlreadyCancelled: true`).
   - Cancelling a completed turn is strictly rejected with `InvalidConversationLifecycleError` (HTTP 409 Conflict).
7. **Strict Error Classification & Information Sanitization**:
   - `AiTurnErrorClassifier` maps runtime errors, provider timeouts, and shutdown signals into structured taxonomy (`TurnFailureCategory`), distinguishing retryable vs non-retryable failures.
   - Sensitive credentials, connection strings, and raw stack traces are stripped before persisting error messages.

## 3. Failure Taxonomy & Classification

`AiTurnErrorClassifier` deterministically classifies generation errors:

| Failure Category        | Retryable | Example Error / Trigger                              | Outcome Persistence                                            |
| :---------------------- | :-------- | :--------------------------------------------------- | :------------------------------------------------------------- |
| `CANCELLATION`          | No        | `AbortError`, `GENERATION_CANCELLED`                 | Turn `CANCELLED`, Attempt `CANCELLED` (`isCanonical: false`)   |
| `GENERATION_TIMEOUT`    | Yes       | `ProviderTimeoutException`, timeout in LLM/embedding | Turn `FAILED`, Attempt `FAILED` (`isCanonical: false`)         |
| `WORKER_SHUTDOWN`       | Yes       | Worker `SIGTERM` / shutdown timeout                  | Turn `PENDING` / lease expires naturally for watchdog recovery |
| `RETRIEVAL_FAILURE`     | Yes       | Vector store connection timeout / transient DB error | Turn `FAILED`, Attempt `FAILED`                                |
| `PERSISTENCE_FAILURE`   | Yes       | Deadlock, transient connection failure in PostgreSQL | Handled by transaction retry or marked `FAILED`                |
| `VALIDATION_FAILURE`    | No        | Malformed turn input / sequence violation            | Turn `FAILED`, Attempt `FAILED`                                |
| `AUTHORIZATION_FAILURE` | No        | Document tenant filter violation                     | Turn `FAILED`, Attempt `FAILED`                                |
| `UNKNOWN_FAILURE`       | No        | Unhandled unexpected runtime exception               | Turn `FAILED`, Attempt `FAILED`                                |

### Information Sanitization

Raw errors are sanitized to prevent credential and topology disclosure:

- Strips connection strings (`postgres://...`, password/auth tokens).
- Strips internal database ports (`5432`) and file paths.
- Returns clean, client-safe error messages.

## 4. Cancellation & Fencing Semantics

### REST Endpoint

- **Route**: `POST /api/v1/ai/conversations/:id/turns/:turnId/cancel`
- **Request Body (Optional)**: `CancelTurnRequestDto` (`{ reason?: string }`)
- **Response**: `CancelTurnResponseDto` (`{ conversationId, turnId, turnStatus: 'CANCELLED', assistantMessageId, isAlreadyCancelled, cancelledAt }`)

### Invariants Enforced

1. **Idempotency**: Repeated cancellation calls for an already cancelled turn return HTTP 200 with `isAlreadyCancelled: true`. No redundant database updates or dispatcher signals are generated.
2. **Terminal Integrity**: Cancelling an already `COMPLETED` turn throws `InvalidConversationLifecycleError`, which the filter maps to HTTP 409 Conflict.
3. **In-Flight Abort Signaling**: If the turn is currently executing in memory, `dispatcher.cancelTurn` calls `abortController.abort(new Error('GENERATION_CANCELLED'))`.
4. **Fencing Protection**: If an LLM call completes after cancellation commits to PostgreSQL, `ExecuteConversationTurnUseCase` re-inspects the turn inside its interactive transaction, detects `inTxTurn.status === 'CANCELLED'`, and rejects the late result without mutating the canonical records.
