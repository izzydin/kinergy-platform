# AI-05: Vector Persistence & Storage Architecture

## 1. Architecture & Hexagonal Decoupling

Vector persistence in Kynergy Platform is decoupled via the Hexagonal boundary `IVectorStorePort` and implemented by `PrismaVectorStoreRepository`:

```
Domain Layer: DocumentEmbedding -> VectorValues ([1024 floats])
                              |
                     IVectorStorePort (Pure Interface)
                              |
Infrastructure: PrismaVectorStoreRepository ($executeRaw / $queryRaw)
                              |
                    PostgreSQL 16 + pgvector (0.8.7)
                   [document_embeddings.embedding vector(1024)]
```

### Decoupling Guarantees

- **Domain Independence**: `@prisma/client`, `vector(1024)`, and raw SQL fragments exist solely within `packages/core/src/ai/infrastructure/persistence/prisma/`.
- **Strict Typing**: Zero `any` casting in vector persistence adapters.
- **Type-Safe Invariants**: Mathematical vector coordinates are validated before hitting SQL serialization.

## 2. Vector Dimension Strategy

### Initial Baseline: 1,024 Dimensions

Empirical tests on the live Ollama runtime confirmed that the approved BGE-M3 model (`bge-m3:latest`, digest `sha256:7907646426...`) generates unit-normalized vectors of exactly **1,024 dimensions**.

### Multi-Layer Dimensional Guard:

1. **Domain Guard (`VectorValues`)**: Checks `values.length === 1024` and rejects `NaN`, `+Infinity`, and `-Infinity`.
2. **Entity Guard (`DocumentEmbedding`)**: Verifies `vector.dimensions === profile.dimensions`.
3. **Database Column Type (`vector(1024)`)**: PostgreSQL native type rejects any vector literal with dimension $\ne 1024$ (`ERROR: expected 1024 dimensions`).
4. **Database Check Constraint**: `CHECK (dimensions = 1024)`.

### Accommodating Future Models (e.g., 768d or 1,536d)

When a future model with different dimensionality is introduced:

- **Approach A (Profile-Partitioned Tables)**: Introduce `document_embeddings_<dims>` (e.g. `document_embeddings_768`) mapped to profiles with matching dimensionality.
- **Approach B (Unconstrained Vector Column with Typed Views)**: Migrate `document_embeddings.embedding` to unconstrained `vector` and create profile-partitioned partial HNSW indexes:
  ```sql
  CREATE INDEX idx_embeddings_768 ON document_embeddings USING hnsw ((embedding::vector(768)) vector_cosine_ops) WHERE profile_id = 'prof_model_768';
  ```
- In all scenarios, the `IndexGeneration` and `EmbeddingProfile` abstractions ensure that search queries never scan across mismatched dimensions.

## 3. High-Performance Indexing: HNSW vs IVFFlat

### Evaluation Matrix

| Metric                      | HNSW (Hierarchical Navigable Small World)     | IVFFlat (Inverted File Flat)                   |
| :-------------------------- | :-------------------------------------------- | :--------------------------------------------- |
| **Recall @ 10**             | **98% - 99.5%**                               | 85% - 92%                                      |
| **Index Build Timing**      | Immediate (Incremental)                       | Requires pre-populated training data (`lists`) |
| **Query Latency**           | $< 5\text{ ms}$                               | $10 - 25\text{ ms}$                            |
| **Memory Footprint**        | Moderate ($\approx 1.2\times$ vector storage) | Low                                            |
| **Suitability for Kynergy** | **APPROVED (Baseline)**                       | Not approved                                   |

### Approved Configuration:

```sql
CREATE INDEX idx_document_embeddings_hnsw
ON document_embeddings USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 64);
```

- Metric: **Cosine Distance** (`vector_cosine_ops`, operator `<=>`).
- Cosine Similarity: $\text{similarity} = 1 - (\text{embedding} \iff \text{query\_vector})$.

## 4. Transactional Design & Invariant Enforcement

1. **Disconnected AI Model Calls**:
   - Embeddings are generated by calling Ollama `/api/embed` **outside** of database transactions.
   - Database transactions are strictly scoped to persistence operations (`saveBatch`), lasting $< 50\text{ ms}$.
2. **Idempotent Batch Upsert**:
   - `saveBatch` utilizes PostgreSQL `INSERT ... ON CONFLICT (chunk_id, index_generation_id) DO UPDATE SET ...` to guarantee safe reprocessing.
3. **Single Active Generation Invariant**:
   - Enforced by partial unique index `unique_active_index_generation_per_tenant`.
   - Direct attempts to insert a second active generation for the same tenant are rejected by the database and mapped to `DuplicateActiveIndexGenerationException`.
4. **Atomic Promotion**:
   - Handled inside `PrismaIndexGenerationRepository.promoteGeneration()` using a serializable transaction that sets the previous generation to `RETIRED` and target to `ACTIVE`.
