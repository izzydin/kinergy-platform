## 1. Executive Summary

Milestone **BE.07.02** proves that conversation data, sequence-ordered message history, turn reservations, generation lifecycles, and privileged supervisory inspection obey the approved multi-tenant and multi-user authorization policies across both HTTP transport and application/persistence domain boundaries.

Verification was executed against a live PostgreSQL database using independent authenticated principals, testing:

1. **Cross-Tenant Hard Isolation**: Strict 404 responses (zero existence disclosure) for unauthorized cross-tenant read, turn reservation, cancellation, title update, and enumeration attempts.
2. **Same-Tenant Peer Access vs. Turn Ownership**: Same-tenant clinicians can read shared conversations by ID, but turn reservation and cancellation are strictly restricted to the conversation creator (`TenantOwnershipViolationError` / HTTP 403). Conversation listing remains strictly user-partitioned (`ListConversationsUseCase`).
3. **Identity Spoofing & Tampering Resistance**: Client-injected body fields (`tenantId`, `userId`, `roles`) are ignored; identity is derived exclusively from the trusted server-side authentication context (`@TrustedAi()`).
4. **Message History & Cursor Safety**: Keyset cursors cannot leak messages across conversations or tenants; malformed or tampered cursors fail safely (`InvalidCursorException` / HTTP 400).
5. **Worker & Retrieval Boundary**: Background execution and canonical history loading enforce tenant scoping prior to RAG invocation. Unvetted documents from foreign tenants are stripped by `AiSourceAttributionService`.
6. **Privileged Inspection & Audit Invariants**: Enforces `@Roles('Owner')` and `@RequirePermissions(PERMISSIONS.AI.CONVERSATIONS_AUDIT)` with a mandatory clinical justification reason ($\ge 10$ characters). Audit logs are committed to PostgreSQL before content is returned, fail-closed behavior prevents data leaks on persistence failure, and audit records survive conversation hard deletion.

## 4. Endpoint & Operation Coverage

Integration tests in `apps/api/src/ai/__tests__/ai-be07-isolation-acceptance.spec.ts` execute real PostgreSQL operations across the entire application and controller surface:

### 4.1 Task 1: Conversation Access Isolation

- **Own Conversation Read**: User A1 reads Conversation A1 $\rightarrow$ Returns HTTP 200 with matching metadata.
- **Same-Tenant Peer Read**: User A2 reads Conversation A1 $\rightarrow$ Returns HTTP 200 (tenant collaboration).
- **Cross-Tenant Read Blocked**: User B1 reads Conversation A1 $\rightarrow$ Throws `ConversationNotFoundError` (HTTP 404, never 403/200).
- **Enumeration Attack Defense**: Probing UUIDs and sequential identifiers across tenant boundary returns 404 for every request.
- **Listing Partitioning**: User A1 lists conversations $\rightarrow$ sees 2 items; User A2 lists $\rightarrow$ sees 1 item; User B1 $\rightarrow$ sees 1 item in Tenant B. Zero leakage between users or tenants.
- **Archived Conversation Turn Guard**: Reserving a turn on an archived conversation throws `InvalidConversationLifecycleError`.

### 4.2 Task 2: Message History Access & Keyset Cursor Tampering

- **Scoped Message History**: User A1 retrieves canonical messages $\rightarrow$ user prompt and assistant response ordered by `sequenceNumber ASC`.
- **Cross-Tenant Message History Blocked**: User B1 retrieves history of Conversation A1 $\rightarrow$ Throws `ConversationNotFoundError` (HTTP 404).
- **Cross-Conversation Cursor Misuse**: Supplying a cursor originating from Conversation 1 to query Conversation 2 filters only within Conversation 2; zero messages from Conversation 1 are leaked.
- **Malformed Cursor Resistance**: Tampered base64 strings and non-numeric sequence cursors throw `InvalidCursorException` (HTTP 400 `AI_INVALID_CURSOR`).

### 4.3 Task 3: Turn Submission, Mutation & Identity Spoofing Defense

- **Cross-Tenant Turn Reservation**: User B1 reserving turn on Conversation A1 throws `ConversationNotFoundError` (HTTP 404).
- **Same-Tenant Peer Turn Reservation**: User A2 reserving turn on Conversation A1 throws `TenantOwnershipViolationError` (HTTP 403). Creator turn ownership strictly preserved.
- **Same-Tenant Peer Turn Cancellation**: User A2 cancelling User A1 generation throws `TenantOwnershipViolationError` (HTTP 403).
- **Cross-Tenant Title Update**: User B1 updating title of Conversation A1 throws `ConversationNotFoundError` (HTTP 404); database title unchanged.
- **Client Identity Spoofing**: Injected body parameters (`tenantId: 'tenant_iso_beta'`, `userId: 'attacker'`, `roles: ['Owner']`) are ignored; database row is created with authenticated `PRINCIPAL_A1` attributes.
- **Cross-Tenant Identifier Reuse**: Reusing identical `clientTurnId` across Tenant A and Tenant B creates independent, isolated turns without collisions.

### 4.4 Task 4: Generation & Retrieval Isolation

- **Worker Tenant Fencing**: Worker calling `ExecuteConversationTurnUseCase` with `tenantId: TENANT_B` targeting a Tenant A turn throws `ConversationNotFoundError` before RAG execution.
- **Canonical History Context Fencing**: `LoadCanonicalConversationHistoryUseCase` called with mismatched tenant returns 404.
- **Attribution Document Boundary**: `AiSourceAttributionService.validateAndSanitize()` strips foreign tenant documents and unvetted chunk IDs.

### 4.5 Task 5: Privileged Inspection & Audit Invariants

- **Controller Guard Verification**: Confirmed `AuthenticationGuard` and `AuthorizationGuard` on controller class; `@Roles('Owner')` and `@RequirePermissions('ai.conversations.audit')` on `auditInspect`.
- **Permission Enforcement**: Principals lacking `ai.conversations.audit` fail authorization evaluation.
- **Non-Owner Application Enforcement**: Calling `PrivilegedInspectConversationUseCase` with non-Owner role throws `TenantOwnershipViolationError`.
- **Justification Validation**: Reasons $< 10$ characters throw `InvalidTurnInputError`.
- **Cross-Tenant Inspection Blocked**: Owner B inspecting Tenant A throws `ConversationNotFoundError` (HTTP 404).
- **Durable Audit Persistence**: Successful inspection commits `AiConversationAuditLog` to PostgreSQL with action `PRIVILEGED_CONVERSATION_INSPECTED`, inspector ID, and reason snapshot.
- **Fail-Closed Protection**: Simulating database failure during audit log save aborts operation (`TransactionFailureError`), returning zero message data.
- **Audit Retention**: Hard deleting the conversation from PostgreSQL leaves the audit log record intact.
