## 1. Executive Summary

Milestone **BE.07.03** proves that concurrent API requests, background workers, and lifecycle mutations executed against real PostgreSQL cannot create inconsistent conversation state, duplicate canonical assistant messages, multiple concurrent active generations on the same thread, or stale worker overwrites.

All tests were executed against the live PostgreSQL database (`DATABASE_URL`) using independent database connections (`prisma1`, `prisma2`, `prisma3`), exercising real row-level transactions, database uniqueness constraints, partial indexes, and transactional fencing tokens without relying on arbitrary sleeps.

### Key Verification Highlights

1. **One-Active-Generation Invariant**:
   - Competing turn reservations on the same conversation are strictly serialized at the PostgreSQL transaction level. Exactly one reservation succeeds; competing requests receive `TurnAlreadyInProgressError` (HTTP 409 Conflict).
   - The PostgreSQL partial unique index `ai_conversation_active_generation_idx` independently blocks any raw database bypass attempting to insert multiple active (`PENDING` or `STREAMING`) assistant messages for the same conversation.
2. **Cancellation vs. Finalization Race**:
   - When cancellation wins, the in-flight worker's finalization transaction fails its fencing guard (`inTxTurn.status === TurnStatus.CANCELLED`). The late LLM answer is discarded, `isCanonical` remains `false`, and `sources` remain `null`.
   - When finalization wins (`TurnStatus.COMPLETED`), subsequent cancellation requests are rejected with `InvalidConversationLifecycleError` (HTTP 409 Conflict). Terminal completed states are immutable.
3. **Stale Worker & Fencing Protection**:
   - If an active attempt number is incremented in PostgreSQL (e.g., worker recovery reassignment), a resuming stale worker detects the attempt discrepancy and aborts with `errorCode: 'ATTEMPT_SUPERSEDED'`. It cannot overwrite the newer attempt.
4. **Concurrent Idempotency**:
   - 4 concurrent requests submitted with the exact same `clientTurnId` and payload on independent connections all resolve cleanly: exactly 1 request creates the turn (`isIdempotentReplay: false`), and the remaining 3 recover the canonical turn (`isIdempotentReplay: true`). In the database, exactly 1 turn row and 2 message rows are created.
   - Concurrent requests with identical `clientTurnId` but conflicting payloads trigger `DuplicateClientTurnPayloadMismatchError` (HTTP 409 Conflict).
5. **Database Constraint Safeguards**:
   - Verified active-generation partial index (`ai_conversation_active_generation_idx`).
   - Verified single user message per turn (`uq_turn_single_user_message`).
   - Verified single canonical assistant message per turn (`uq_turn_single_canonical_assistant`).
   - Verified canonical requires success check constraint (`chk_canonical_requires_success`).
   - Verified immutable sequence uniqueness (`ai_conversation_messages_conversation_id_sequence_number_key`).

## 2. Concurrency Scenarios & Synchronization Design

To guarantee deterministic, repeatable verification without non-deterministic timing, a custom `Barrier` synchronization primitive and independent database connections were utilized:

```
[Client Thread 1 (prisma1)]         [Client Thread 2 (prisma2)]          [PostgreSQL Engine]
          │                                     │                                 │
          ├─────── reserveTurnUseCase ──────────┼────────────────────────────────►│ (Atomic Tx: Row Lock)
          │                                     ├────── reserveTurnUseCase ──────►│ (Blocked on conv lock)
          │◄────── 201 Created (Success) ───────┼─────────────────────────────────┤
          │                                     │◄───── 409 Conflict (Rejected) ──┤ (TurnAlreadyInProgress)
          │                                     │                                 │
```

For worker finalization races, a controllable `IRAGTurnPipelinePort` adapter hooked into execution lifecycle events:

1. `onRagExecutionStarted`: Triggers a release barrier when the worker enters inference.
2. `ragExecutionBarrier`: Pauses worker execution while the competing thread (e.g. cancellation) commits its state transition in PostgreSQL.
3. Releasing `ragExecutionBarrier` lets the worker attempt its finalization transaction, exercising the real fencing guard against PostgreSQL.

## 4. Competing Operation Outcomes & Assertions

Integration tests in `apps/api/src/ai/__tests__/ai-be07-concurrency-acceptance.spec.ts` prove the following outcomes:

### 4.1 Task 1: Concurrent Turn Reservation Races

- **2-Way Race**: Fired simultaneous `reserveTurnUseCase.execute` calls across `prisma1` and `prisma2`.
  - **Winner**: Returns `ReserveConversationTurnResult` (`turnIndex: 2`, `status: PENDING`).
  - **Loser**: Throws `TurnAlreadyInProgressError` (HTTP 409 Conflict).
  - **PostgreSQL Assertions**: Exactly 2 turn rows exist (`turnIndex: 1` COMPLETED, `turnIndex: 2` PENDING). Exactly 4 messages exist with sequence numbers `[1, 2, 3, 4]`. No orphaned user prompt.
- **3-Way Race**: Fired simultaneous requests across `prisma1`, `prisma2`, and `prisma3`.
  - **Winner**: Exactly 1 request succeeds.
  - **Losers**: Exactly 2 requests throw `TurnAlreadyInProgressError`.
  - **PostgreSQL Assertions**: Exactly 1 active turn (`status IN ('PENDING', 'STREAMING')`) exists in the conversation.

### 4.2 Task 2: Active-Generation Exclusivity

- **Database Level Enforcement**: Attempted raw SQL insert of a second active assistant message on a conversation with an existing `PENDING` assistant placeholder.
  - **PostgreSQL Outcome**: Immediate rejection with PostgreSQL error code `23505` (`unique_violation` on `ai_conversation_active_generation_idx`).
- **Parallel Independent Conversations**: Two distinct conversations create and reserve active generation turns simultaneously. Both succeed independently with zero cross-blocking or resource contention.

### 4.3 Task 3: Cancellation vs Successful Finalization

- **Cancellation Wins**:
  - Worker begins LLM inference; pauses at barrier.
  - Client cancels turn via Connection 2 (`CancelConversationTurnUseCase`). Turn and assistant transition to `CANCELLED` in PostgreSQL.
  - Worker barrier released; worker attempts atomic finalization.
  - **Outcome**: Fencing check rejects finalization. Worker returns `outcome: CANCELLED, errorCode: 'GENERATION_CANCELLED'`.
  - **PostgreSQL Assertions**: Turn status remains `CANCELLED`, assistant message remains `CANCELLED`, `isCanonical` remains `false`, and `sources` remain `null`. The late answer is never persisted.
- **Finalization Wins**:
  - Worker finalizes turn first (`status: COMPLETED`, assistant `status: SUCCESS, isCanonical: true`).
  - Late cancellation arrives via Connection 2.
  - **Outcome**: Cancellation use case throws `InvalidConversationLifecycleError` (HTTP 409 Conflict: "Cannot cancel turn because it has already COMPLETED").
  - **PostgreSQL Assertions**: Turn remains `COMPLETED`, canonical message remains immutable `SUCCESS`.

### 4.4 Task 4: Stale Worker & Fencing Protection (Superseded Attempt)

- Worker begins execution on Attempt 1; pauses at barrier.
- Background process updates `active_attempt_number = 2` in PostgreSQL.
- Worker resumes and attempts finalization with Attempt 1 credentials.
- **Outcome**: Transactional fencing guard detects `inTxTurn.activeAttemptNumber !== assistantAttempt.attemptNumber`. Returns `errorCode: 'ATTEMPT_SUPERSEDED'`.
- **PostgreSQL Assertions**: Attempt 1 is not canonicalized; authoritative recovery attempt is protected.

### 4.5 Task 5: Concurrent Idempotency Requests

- **Identical Payload Race**: 4 simultaneous requests submitted with the exact same `clientTurnId` and payload across independent connections.
  - **Outcome**: All 4 requests resolve cleanly. Exactly 1 request has `isIdempotentReplay: false` (the creator); the remaining 3 have `isIdempotentReplay: true`. All 4 return identical `conversationId` and `turnId`.
  - **PostgreSQL Assertions**: Exactly 1 turn row exists for that `clientTurnId`; exactly 1 user message and 1 assistant placeholder exist.
- **Conflicting Payload Race**: 2 simultaneous requests submitted with the same `clientTurnId` but conflicting prompts.
  - **Outcome**: Exactly 1 request succeeds; the competing request throws `DuplicateClientTurnPayloadMismatchError` (HTTP 409 Conflict).

### 4.6 Task 6: Conversation & Message Consistency

- Executed 4 successive rapid turns through complete lifecycle.
- **PostgreSQL Assertions**: All 8 messages have unique, monotonically ascending sequence numbers `[1, 2, 3, 4, 5, 6, 7, 8]`. Conversation counters (`turnCounter: 4`, `messageCounter: 8`) match committed rows exactly. Keyset pagination returns deterministic, gap-free results.

### 4.7 Task 7: Direct Database Constraint & Invariant Verification

- Verified raw SQL rejection on:
  1. Inserting 2 user messages for the same turn $\rightarrow$ Rejection `23505` (`uq_turn_single_user_message`).
  2. Marking 2 assistant messages canonical for the same turn $\rightarrow$ Rejection `23505` (`uq_turn_single_canonical_assistant`).
  3. Setting `is_canonical = TRUE` on non-SUCCESS status $\rightarrow$ Rejection on check constraint `chk_canonical_requires_success`.
