## 1. Executive Summary

This report documents the design, implementation, and empirical verification of `CreateConversationWithInitialTurnUseCase` within `packages/core/src/ai/application/use-cases/create-conversation-with-initial-turn.use-case.ts`.

The use case achieves full transactional atomicity for conversation initialization:

1. **Four-Aggregate Atomic Persistence:** Creates the parent `AiConversation`, initial `AiConversationTurn` (index #1), initial `AiConversationMessage` (User prompt, sequence #1, status SUCCESS), and assistant placeholder `AiConversationMessage` (Assistant attempt #1, sequence #2, status PENDING), guaranteed by a single interactive transaction boundary.
2. **Deterministic Payload Hashing:** Canonicalizes user prompt text (whitespace trimming and `\r\n` to `\n` normalization) and metadata property order, producing a cryptographically collision-resistant SHA-256 hex hash stored on the turn.
3. **Robust Idempotency Arbitration:** Detects retries via `clientTurnId`. Same payload yields the existing conversation and turn state (`EXISTING_RECOVERED`), while mismatched payloads raise a typed `DuplicateClientTurnPayloadMismatchError`.
4. **PostgreSQL Concurrency Arbitration:** Resolves concurrent duplicate initial requests across independent database connections without race conditions or orphaned records, leveraging PostgreSQL unique constraints (`uq_turn_tenant_client_turn_id` and `uq_conversation_user_idempotency`) and controlled commit polling.
5. **Atomic Sequence Allocation:** Employs aggregate-level monotonic counters (`turnCounter`, `messageCounter`) on `AiConversation`, avoiding anti-patterns such as `MAX(sequence) + 1` or external sequences.

## 2. Workflow Description

```
Client Request
      │
      ▼
Input Validation (tenantId, userId, clientTurnId, non-empty userPrompt)
      │
      ▼
Deterministic Payload Hashing (Canonical prompt + metadata -> SHA-256)
      │
      ▼
Preliminary Fast-Path Idempotency Check (turnRepo.findByClientTurnId)
 ├─ Found & Matching Hash: Return EXISTING_RECOVERED (isIdempotentReplay: true)
 ├─ Found & Mismatched Hash: Throw DuplicateClientTurnPayloadMismatchError
 └─ Not Found: Proceed to Transaction
      │
      ▼
Atomic Transaction Execution (txRunner.runInTransaction)
 ├─ Guard check within TX (findByClientTurnId)
 ├─ Derive Title: ConversationTitle.deriveFromPrompt (first 40 characters)
 ├─ Allocate Counters: turnCounter -> 1, messageCounter -> 1 (user), 2 (assistant)
 ├─ Persist AiConversation
 ├─ Persist AiConversationTurn (index 1, status PENDING)
 ├─ Persist AiConversationMessage (role USER, seq 1, status SUCCESS)
 ├─ Persist AiConversationMessage (role ASSISTANT, seq 2, status PENDING)
 ├─ Associate Turn Active Attempt (turn.associateActiveAttempt -> assistantMsg.id)
 ├─ Update Turn with Active Attempt Pointer
 └─ Return CREATED (isIdempotentReplay: false)
      │
      ▼ (On Unique Constraint Race)
Catch Unique Violation (uq_turn_tenant_client_turn_id / uq_conversation_user_idempotency)
 ├─ Await winning transaction commit
 ├─ Query committed turn & verify payload hash
 ├─ Matching: Return EXISTING_RECOVERED
 └─ Mismatch: Throw DuplicateClientTurnPayloadMismatchError
```

## 3. Transaction Boundary & Atomicity Guarantees

All persistence operations execute strictly inside `this.txRunner.runInTransaction(async (repos) => { ... })`:

- Repositories (`conversationRepo`, `turnRepo`, `messageRepo`, `auditRepo`) are scoped to the active Prisma transaction client (`.withTransaction(tx)`).
- **Foreign Key Ordering:** To satisfy foreign key constraints before the assistant message exists, the turn is persisted first with `activeAttemptId: null`. After user and assistant messages are persisted, the turn's active attempt reference is associated and persisted. PostgreSQL's deferred constraint trigger (`trg_validate_turn_active_attempt`) enforces that `active_attempt_id` belongs to an ASSISTANT message in the exact same turn/conversation/tenant at commit time.
- **Rollback Guarantee:** If any step fails (or if the database connection drops before commit), the entire unit of work aborts. Zero empty conversations, zero orphaned turns, and zero incomplete messages can ever be left behind in PostgreSQL.

## 4. Idempotency Behavior & Arbitration

### 4.1 Replay with Identical Payload

When a request arrives with a `clientTurnId` that has already been committed and the computed payload hash matches:

- Fast-path check bypasses transaction initiation.
- The committed conversation, turn, user message, and assistant attempt are retrieved.
- Returns `CreateConversationWithInitialTurnResult` with:
  - `isIdempotentReplay: true`
  - `idempotencyOutcome: 'EXISTING_RECOVERED'`
  - Original IDs, sequence numbers, and timestamps.
- Zero new records are inserted in PostgreSQL.

### 4.2 Replay with Mismatched Payload

When an existing `clientTurnId` is submitted with a different prompt or metadata:

- The computed hash differs from the stored `idempotencyPayloadHash`.
- Throws typed `DuplicateClientTurnPayloadMismatchError` specifying `clientTurnId`, `existingHash`, and `receivedHash`.
- The existing conversation in the database remains completely untouched.

### 4.3 Concurrent Duplicate Creation Requests

When two or more requests arrive simultaneously with the same `(tenantId, clientTurnId)` across separate app instances or connections:

- Both pass the preliminary check because neither has committed.
- Both enter separate transactions.
- PostgreSQL unique constraint arbitration stops the loser:
  - Either `uq_conversation_user_idempotency` fails on `ai_conversations`, or
  - `uq_turn_tenant_client_turn_id` fails on `ai_conversation_turns`.
- The losing transaction rolls back immediately with code `P2002` / `23505`.
- The use case catches the uniqueness conflict, waits for the winning transaction to finish commit, recovers the committed turn, verifies the payload hash, and returns `EXISTING_RECOVERED`.
- Exactly one conversation is created; neither client experiences an unhandled failure.

## 5. Payload-Hashing Strategy

Implemented in [`packages/core/src/ai/application/services/ai-payload-hasher.ts`](file:///c:/Projects/kinergy-platform/packages/core/src/ai/application/services/ai-payload-hasher.ts):

1. **Whitespace & Formatting Normalization:**
   - Leading and trailing whitespace is stripped (`prompt.trim()`).
   - Line endings are normalized: `\r\n` is converted to `\n`.
   - Internal spaces and intentional indentation (such as code blocks or lists) are preserved.
2. **Metadata Canonicalization:**
   - If `metadata` is provided, object keys are sorted lexicographically at every recursive depth.
   - Transient fields (timestamps, request IDs, authentication tokens) are prohibited.
3. **Cryptographic Algorithm:**
   - Generates a 64-character SHA-256 hexadecimal string using the environment's cryptographic provider.
   - Stored directly in `ai_conversation_turns.idempotency_payload_hash` (VARCHAR(64)).

## 6. Sequence Allocation Strategy

- **Monotonic Counters on Aggregate Root:**
  - `AiConversation.turnCounter` tracks turn sequences (`turnIndex = 1, 2, ...`).
  - `AiConversation.messageCounter` tracks message sequences across the entire conversation (`sequenceNumber = 1, 2, ...`).
- **No `MAX(sequence) + 1`:** Sequence allocation occurs by calling `.incrementMessageCounter()` on the conversation aggregate inside the transaction boundary, locked by the row-level update on `AiConversation`.
- **Initial Allocation:**
  - Initial turn: `turnIndex = 1`.
  - User prompt message: `sequenceNumber = 1`.
  - Assistant placeholder message: `sequenceNumber = 2`.
  - Final conversation state: `turnCounter = 1, messageCounter = 2`.
