## 2. Alpine (musl) to Debian (glibc) Binary Compatibility Analysis

### 2.1 The Architectural Challenge

The previous container was `postgres:16-alpine` (PostgreSQL 16.14 compiled against Alpine's `musl` libc). The new container is `pgvector/pgvector:pg16` (PostgreSQL 16.16 compiled against Debian 12 Bookworm's `glibc`).

In PostgreSQL, switching the C runtime library across major versions or collation providers can affect `libc`-based text collation indexes.

### 2.2 Empirical Safety Verification in Kinergy Platform

1. **Collation Mode:** The database cluster was initialized with standard `C.UTF-8` / `en_US.utf8` collations.
2. **PostgreSQL Version Parity:** Both engines operate within the **PostgreSQL 16 major version family** (16.14 $\rightarrow$ 16.16). PostgreSQL's disk on-page layout, catalog OIDs, tuple headers, and WAL records are 100% binary compatible between minor revisions.
3. **WAL Replay Test:** Mounting the existing volume directly into `pgvector/pgvector:pg16` resulted in flawless automatic WAL replay:
   $$\text{Checkpoint Complete} \longrightarrow \text{Zero Corrupted Blocks} \longrightarrow \text{Accepting Connections}$$
4. **Data Verification:** All 19 historical `_prisma_migrations` records, foreign keys, table indexes, and user accounts remained completely accessible. Zero collation version mismatch warnings were logged.

## 3. Least-Privilege Role-Based Access Control (RBAC) Compatibility

The staging RBAC specification in `infrastructure/docker/init-staging-roles.sql` enforces strict separation of concerns across database users:

### 3.1 Role Capabilities Matrix

| Role                        | Intended Context                 |           DDL Permissions           |              DML Permissions               |         Extension Creation          |
| :-------------------------- | :------------------------------- | :---------------------------------: | :----------------------------------------: | :---------------------------------: |
| **`kinergy_staging_admin`** | Superuser / DBA                  |            Full (`ALL`)             |                Full (`ALL`)                | **Permitted** (`CREATE EXTENSION`)  |
| **`kinergy_migrator`**      | CI/CD Pre-deploy Migrations      | Schema DDL (`ALL ON SCHEMA public`) |         Full DML on Public Tables          | Inherits extension from init script |
| **`kinergy_app`**           | NestJS Runtime (Least-Privilege) |  **REVOKED** (`CREATE ON SCHEMA`)   |      `SELECT, INSERT, UPDATE, DELETE`      |           **Prohibited**            |
| **`kinergy_test`**          | Integration Test Runner          |             **REVOKED**             | `SELECT, INSERT, UPDATE, DELETE, TRUNCATE` |           **Prohibited**            |

### 3.2 Extension Creation Boundary

Because the `vector` extension requires superuser privileges to activate (not flagged as `trusted` in PostgreSQL catalog), the extension creation is executed during container initialization by the database admin/superuser via:

1. `init-db.sql` (Development / Demo / Production).
2. `init-staging-roles.sql` (Staging).
3. Superuser execution for pre-existing running volumes.

This guarantees that application runtimes (`kinergy_app`) remain strictly confined to DML queries and cannot alter extensions, tables, or database catalogs.
