## 2. Issue 01 — Enforce Complete Database Relationships

### 2.1 Problem Analysis

In the previous draft:

1. `userMessageId` and `canonicalMessageId` on `ConversationTurn` were loose string fields without database-level foreign key enforcement.
2. A message could point to a valid `turnId` without verifying that its `conversationId` and `tenantId` matched the turn.
3. The canonical assistant message was not guaranteed to belong to the same turn and conversation, or to possess `role = 'ASSISTANT'`.

### 2.2 Corrected Relational Model & Database Constraints

```
ai_conversations (id, tenant_id)
      │
      │ 1:N (enforced via composite FK: conversation_id, tenant_id)
      ▼
ai_conversation_turns (id, conversation_id, tenant_id)
      │
      │ 1:N (enforced via composite FK: turn_id, conversation_id, tenant_id)
      ▼
ai_conversation_messages (id, turn_id, conversation_id, tenant_id, role)
      ▲
      │ Circular role-safe references (enforced via deferred FKs)
      ├─ user_message_id (role = 'USER')
      └─ canonical_message_id (role = 'ASSISTANT')
```

### 2.4 Exact Raw PostgreSQL SQL for Constraints Beyond Prisma Syntax

Because Prisma cannot represent check-constrained composite foreign keys and `DEFERRABLE INITIALLY DEFERRED` circular constraints, the migration adds the following exact DDL:

```sql
-- 1. Check constraints enforcing static role values on ConversationTurn pointers
ALTER TABLE "ai_conversation_turns"
ADD CONSTRAINT "chk_turn_user_msg_role"
CHECK ("user_message_role" = 'USER');

ALTER TABLE "ai_conversation_turns"
ADD CONSTRAINT "chk_turn_canonical_msg_role"
CHECK ("canonical_message_role" = 'ASSISTANT');

-- 2. Deferrable Circular Foreign Key: user_message_id -> ai_conversation_messages
-- Guarantees user_message_id belongs to the exact turn_id and has role = 'USER'
ALTER TABLE "ai_conversation_turns"
ADD CONSTRAINT "fk_turn_user_message"
FOREIGN KEY ("user_message_id", "id", "user_message_role")
REFERENCES "ai_conversation_messages"("id", "turn_id", "role")
ON DELETE RESTRICT
DEFERRABLE INITIALLY DEFERRED;

-- 3. Deferrable Circular Foreign Key: canonical_message_id -> ai_conversation_messages
-- Guarantees canonical_message_id belongs to the exact turn_id and has role = 'ASSISTANT'
ALTER TABLE "ai_conversation_turns"
ADD CONSTRAINT "fk_turn_canonical_message"
FOREIGN KEY ("canonical_message_id", "id", "canonical_message_role")
REFERENCES "ai_conversation_messages"("id", "turn_id", "role")
ON DELETE SET NULL
DEFERRABLE INITIALLY DEFERRED;
```

### 2.5 Invariant Guarantee Analysis

1. **Turn Tenant Isolation:** `(conversation_id, tenant_id) REFERENCES ai_conversations(id, tenant_id)`. Turn cannot belong to another conversation or tenant.
2. **Message Tenant & Conversation Isolation:** `(turn_id, conversation_id, tenant_id) REFERENCES ai_conversation_turns(id, conversation_id, tenant_id)`. Message cannot belong to another turn, conversation, or tenant.
3. **Role & Turn Integrity on Pointers:** `(user_message_id, id, user_message_role) REFERENCES ai_conversation_messages(id, turn_id, role)`. A turn's user message is physically guaranteed to be a message belonging to _that exact turn_ with `role = 'USER'`.
4. **Canonical Answer Integrity:** `(canonical_message_id, id, canonical_message_role) REFERENCES ai_conversation_messages(id, turn_id, role)`. The canonical answer is physically guaranteed to be a message belonging to _that exact turn_ with `role = 'ASSISTANT'`.

## 3. Issue 02 — Make Sequence and Turn Allocation Concurrency-Safe

### 3.1 Problem Analysis

`SELECT MAX(sequence)` allows concurrent transactions to read the same max value before either commits, causing sequence collisions. Holding a long-running transaction with `SELECT FOR UPDATE` across an LLM inference stalls the database connection pool (pool size is typically 10–20 connections).

### 3.2 Atomic Conversation Counter Strategy

We introduce two atomic monotonic counters on `ai_conversations`:

- `next_sequence INT NOT NULL DEFAULT 1`: Allocates physical sequence numbers.
- `next_turn_number INT NOT NULL DEFAULT 1`: Allocates logical turn numbers.

Inside a short interactive transaction (`< 5ms` execution time):

```sql
UPDATE "ai_conversations"
SET "next_sequence" = "next_sequence" + 2,
    "next_turn_number" = "next_turn_number" + 1,
    "last_activity_at" = NOW(),
    "updated_at" = NOW()
WHERE "id" = $conversationId
  AND "tenant_id" = $tenantId
  AND "deleted_at" IS NULL
RETURNING
    ("next_sequence" - 2) AS "allocated_user_sequence",
    ("next_sequence" - 1) AS "allocated_assistant_sequence",
    ("next_turn_number" - 1) AS "allocated_turn_number";
```

### 3.3 Concurrency Scenarios

#### Scenario A: Two Different Requests Submit New Turns Simultaneously

1. Request 1 begins transaction $T_1$; executes atomic counter update. PostgreSQL acquires row lock on `ai_conversations` record.
2. Request 2 begins transaction $T_2$; executes atomic counter update. $T_2$ pauses in PostgreSQL waiting for $T_1$.
3. $T_1$ allocates `userSeq=1`, `asstSeq=2`, `turnNumber=1`. Inserts Turn 1, User Message 1, Assistant Placeholder 2 (status: `PENDING`).
4. $T_1$ commits (duration: ~3ms). Lock released.
5. $T_2$ resumes immediately. Checks active generation partial index. Finds Assistant Placeholder 2 with status `PENDING`.
6. $T_2$ rolls back immediately. Returns **HTTP 409 Conflict** (`ACTIVE_GENERATION_IN_PROGRESS`). Zero sequence gaps, zero orphaned messages.

#### Scenario B: Two Identical Requests Submit Same Idempotency Identity Simultaneously

1. Request 1 begins transaction $T_1$; inserts conversation or turn with `idempotencyKey = K`.
2. Request 2 begins transaction $T_2$; attempts to insert with same `idempotencyKey = K`.
3. $T_2$ encounters unique constraint violation (`23505`).
4. Catch block catches `23505`, rolls back $T_2$, fetches the committed turn from $T_1$, verifies payload hash, and returns the canonical existing turn (HTTP 200). Exactly one operation created.

#### Scenario C: Turn Reservation Fails After Sequence Allocation

1. Transaction allocates sequences, but user message insertion fails (e.g. database disk error or process kill).
2. Transaction rolls back. In PostgreSQL, row updates inside an uncommitted transaction are rolled back cleanly. `next_sequence` remains unchanged. Zero sequence gaps.

#### Scenario D: Previous Turn Failed and User Submits a Retry

1. Previous Turn $N$ failed (`status = 'ERROR'`). No active `PENDING` or `STREAMING` message exists.
2. Client submits retry for Turn $N$.
3. Transaction allocates `next_sequence = next_sequence + 1` (allocating 1 sequence for the new assistant attempt):
   ```sql
   UPDATE "ai_conversations"
   SET "next_sequence" = "next_sequence" + 1,
       "last_activity_at" = NOW()
   WHERE "id" = $conversationId
   RETURNING ("next_sequence" - 1) AS "allocated_assistant_sequence";
   ```
4. Inserts new assistant message with `turnId = turnN.id`, `turnNumber = N`, `turnAttempt = previousAttempt + 1`, `sequence = allocated_assistant_sequence`, `status = 'PENDING'`.
5. Commits. Monotonic ordering preserved: Attempt 2 has higher sequence than Attempt 1.

## 4. Issue 03 — Complete Request Idempotency for All Generation Requests

### 4.1 Unified Request Identity Structure

Every generation request operates under a strict persisted request identity:

```text
Request Identity:
├── tenantId (from authenticated JWT)
├── userId (from authenticated JWT)
├── conversationId (from path parameter or null for first message)
├── idempotencyKey (from Idempotency-Key HTTP header)
└── idempotencyPayloadHash (SHA-256 of canonicalized request options)
```

### 4.2 Canonical Payload Fingerprint Algorithm

```typescript
import * as crypto from 'crypto';

export interface CanonicalGenerationPayload {
  prompt: string;
  searchMode: 'HYBRID' | 'SEMANTIC' | 'KEYWORD';
  topK: number;
  minSimilarity: number;
  model: string;
  temperature: number;
}

export function computePayloadFingerprint(dto: {
  query: string;
  searchMode?: string;
  topK?: number;
  minSimilarity?: number;
  model?: string;
  temperature?: number;
}): string {
  // Normalize strings and round numeric values to prevent floating-point discrepancies
  const canonical: CanonicalGenerationPayload = {
    prompt: dto.query.trim().normalize('NFKC'),
    searchMode: (dto.searchMode?.toUpperCase() as any) ?? 'HYBRID',
    topK: Math.max(1, Math.min(50, dto.topK ?? 5)),
    minSimilarity: Number((dto.minSimilarity ?? 0.6).toFixed(4)),
    model: (dto.model ?? 'qwen3:4b').trim().toLowerCase(),
    temperature: Number((dto.temperature ?? 0.2).toFixed(2)),
  };

  return crypto
    .createHash('sha256')
    .update(JSON.stringify(canonical, Object.keys(canonical).sort()))
    .digest('hex');
}
```

_Excluded fields:_ `clientMessageId`, `clientTurnId`, timestamps, UI telemetry (they do not affect inference outcome).

### 4.3 Comprehensive Idempotency Behavior Matrix

| Scenario                            | Server State                                       | Action Taken                                                                     | HTTP Response                                |
| :---------------------------------- | :------------------------------------------------- | :------------------------------------------------------------------------------- | :------------------------------------------- |
| **New Identity (First Msg)**        | No match on `(tenantId, userId, idempotencyKey)`   | Creates `Conversation`, Turn 1, User Msg 1, Asst Msg 2 atomically.               | `200 OK` (Stream begins)                     |
| **New Identity (Existing Chat)**    | No match on `(conversationId, clientTurnId)`       | Creates Turn $N$, User Msg, Asst Msg atomically.                                 | `200 OK` (Stream begins)                     |
| **Same Key, Same Hash (In Flight)** | Record exists, status is `PENDING` or `STREAMING`  | Reconnects to active generation stream or returns current status.                | `200 OK`                                     |
| **Same Key, Same Hash (Completed)** | Record exists, status is `COMPLETED`               | Returns canonical persisted answer with citations and telemetry.                 | `200 OK`                                     |
| **Same Key, Same Hash (Failed)**    | Record exists, status is `FAILED` or `INTERRUPTED` | Returns existing error record. If `retryAllowed = true`, permits explicit retry. | `200 OK`                                     |
| **Same Key, Different Hash**        | Record exists, but hash differs                    | **Conflict.** Rejects attempt to reuse idempotency key with conflicting query.   | `409 Conflict` (`IDEMPOTENCY_KEY_COLLISION`) |
| **Two Concurrent Submissions**      | Both attempt insert simultaneously                 | One succeeds; second catches `23505`, loads committed record, verifies hash.     | `200 OK` (Canonical replay)                  |

## 5. Issue 04 — Make Generation Leases Safe Against Stale Workers

### 5.1 Fenced Lease Protocol

To prevent stale workers (e.g. paused by GC, network lag, or process restart) from committing over recovered state, every lease acquisition generates a unique cryptographic **`leaseToken` (UUID v4)**:

- `leaseToken`: Acts as an explicit fencing token.
- `leaseOwnerInstanceId`: `hostname_pid_uuid`.
- `leaseExpiresAt`: Strict absolute expiration timestamp.

### 5.2 Timeout Architecture Math

- `retrievalTimeoutMs`: 5,000 ms.
- `contextBuilderTimeoutMs`: 1,000 ms.
- `generationTimeoutMs`: 20,000 ms.
- `requestTimeoutMs`: 30,000 ms (total execution deadline).
- **Lease Duration:** 30,000 ms (30 seconds). Matches maximum execution deadline.
- **Heartbeat Frequency:** Every 10,000 ms (10 seconds). During active streaming, the worker renews the lease every 10s, providing two retry opportunities before expiration.
- **Recovery Worker Polling:** Every 15,000 ms (15 seconds).

### 5.3 Concrete Operational SQL & Procedures

#### A. Lease Acquisition (Inside Turn Reservation Transaction)

```sql
UPDATE "ai_conversation_messages"
SET "lease_token" = $generatedLeaseToken,
    "lease_owner_instance_id" = $myInstanceId,
    "lease_expires_at" = NOW() + INTERVAL '30 seconds',
    "status" = 'PENDING'
WHERE "id" = $assistantMessageId;
```

#### B. Heartbeat Renewal (Every 10s during streaming)

```sql
UPDATE "ai_conversation_messages"
SET "lease_expires_at" = NOW() + INTERVAL '30 seconds'
WHERE "id" = $assistantMessageId
  AND "lease_token" = $myLeaseToken
  AND "status" IN ('PENDING', 'STREAMING')
  AND "lease_expires_at" > NOW();
```

_Invariant:_ If `rowsAffected === 0`, the lease was revoked or expired. The worker immediately halts inference.

#### C. Recovery Claiming (Atomic Transition of Message & Turn)

```sql
WITH reclaimed_messages AS (
  UPDATE "ai_conversation_messages"
  SET "status" = 'INTERRUPTED',
      "error_code" = 'LEASE_EXPIRED_OR_WORKER_CRASH',
      "error_message" = 'La generación fue interrumpida por tiempo límite o reinicio del sistema.',
      "lease_token" = NULL,
      "lease_owner_instance_id" = NULL,
      "lease_expires_at" = NULL
  WHERE "status" IN ('PENDING', 'STREAMING')
    AND "lease_expires_at" < NOW()
  RETURNING "id", "turn_id", "conversation_id"
)
UPDATE "ai_conversation_turns"
SET "status" = 'INTERRUPTED',
    "updated_at" = NOW()
WHERE "id" IN (SELECT "turn_id" FROM reclaimed_messages);
```

_Invariant:_ Transitions **both** `ConversationMessage` and `ConversationTurn` atomically in a single statement. Multiple API replicas executing this concurrently execute safe PostgreSQL row-level locks without duplicate transitions.

#### D. Successful Generation Commit

```sql
UPDATE "ai_conversation_messages"
SET "status" = 'SUCCESS',
    "content" = $canonicalAnswer,
    "sources" = $sourcesJson,
    "metadata" = $telemetryJson,
    "lease_token" = NULL,
    "lease_owner_instance_id" = NULL,
    "lease_expires_at" = NULL
WHERE "id" = $assistantMessageId
  AND "lease_token" = $myLeaseToken
  AND "status" IN ('PENDING', 'STREAMING');

-- Followed by Turn completion
UPDATE "ai_conversation_turns"
SET "status" = 'COMPLETED',
    "canonical_message_id" = $assistantMessageId,
    "updated_at" = NOW()
WHERE "id" = $turnId;
```

#### E. Stale Worker Attempting to Commit

If a worker was paused for 40 seconds and attempts to commit after recovery claimed its generation:

- The `WHERE lease_token = $myLeaseToken AND status IN ('PENDING', 'STREAMING')` condition yields `rowsAffected === 0`.
- The stale worker detects `rowsAffected === 0`, rolls back, logs a warning, and discards the generated content without corrupting database state.

## 6. Issue 05 — Define the Required Partial Unique Index

### 6.1 PostgreSQL DDL Definition

The active-generation invariant is enforced by a PostgreSQL partial unique B-Tree index:

```sql
CREATE UNIQUE INDEX "ai_conversation_active_generation_idx"
ON "ai_conversation_messages" ("conversation_id")
WHERE "role" = 'ASSISTANT' AND "status" IN ('PENDING', 'STREAMING');
```

### 6.2 Pre-Migration Data Cleanup Invariant

If this index is applied to an existing database containing orphaned active generations, the migration script executes pre-cleanup:

```sql
UPDATE "ai_conversation_messages"
SET "status" = 'INTERRUPTED',
    "error_code" = 'MIGRATION_CLEANUP_ORPHAN',
    "error_message" = 'Generación huérfana limpiada durante actualización de esquema.'
WHERE "role" = 'ASSISTANT' AND "status" IN ('PENDING', 'STREAMING');
```

### 6.3 Behavior & Error Translation

- Exactly **one** active generation attempt is permitted per conversation at any given time.
- Failed, cancelled, and interrupted attempts have `status NOT IN ('PENDING', 'STREAMING')`, so they are excluded from the index and preserved in history.
- When a concurrent attempt violates this index, PostgreSQL emits error `23505` with index name `ai_conversation_active_generation_idx`.
- The exception filter translates this directly to:
  ```json
  {
    "statusCode": 409,
    "error": "Conflict",
    "code": "ACTIVE_GENERATION_IN_PROGRESS",
    "message": "Ya existe una generación clínica en curso para esta conversación. Espera a que finalice antes de enviar una nueva consulta."
  }
  ```

## 7. Issue 06 — Correct Conversation Pagination Consistency Claims

### 7.1 Selection: Option C (Explicit Eventual-Consistency Keyset Pagination)

- **Technical Reality:** When a conversation receives a new message, its `lastActivityAt` timestamp increases, moving it to the top of the conversation list.
- **Why Snapshot Pagination is Rejected:** PostgreSQL snapshot export (`SET TRANSACTION SNAPSHOT`) requires holding open transactions across multiple client HTTP requests, which exhausts database connection pool connections.
- **The Selected Contract:**
  1. **Cursor Structure:** Base64-encoded tuple `btoa("${lastActivityAt.toISOString()}_${id}")`.
  2. **Query:**
     ```sql
     WHERE tenant_id = $1
       AND user_id = $2
       AND deleted_at IS NULL
       AND (last_activity_at < $cursorTime OR (last_activity_at = $cursorTime AND id < $cursorId))
     ORDER BY last_activity_at DESC, id DESC
     LIMIT $limit;
     ```
  3. **Consistency Guarantees:**
     - A conversation modified _after_ page 1 was loaded moves to `last_activity_at > cursorTime`. It will **not** appear on page 2.
     - When the user returns to the top or triggers refresh, the updated conversation appears at the top.
     - **Client Deduplication:** The TanStack Query client cache deduplicates conversations by `id` on every merge, ensuring zero UI duplicate items.
  4. **Message History Consistency:**
     - Message history pagination uses `sequence < beforeSequence`. Because sequence numbers are immutable and monotonic, newly appended messages have **zero impact** on historical pagination offsets.

## 8. Issue 07 — Correct Authorization and Clinical Audit Semantics

### 8.1 Role Taxonomy in Kynergy

Verified from `apps/api/src/platform/identity/authorization/permissions.ts`:

- **`Owner`:** **Tenant Owner / Administrator** (`tenantId` is stamped on `users`). Kynergy is a multi-tenant platform; `Owner` has full operational access _strictly within their own tenant_. Cross-tenant access is prohibited.
- **`Trainer`, `Therapist`, `Receptionist`, `Kitchen Staff`:** Operational Clinical Staff.
- **Conversation Owner:** The specific clinician (`userId`) who initiated the consultation.

### 8.2 Clinical Audit Event Definition

```typescript
export enum AuditEventType {

  // Data Access & Clinical Privacy Events

}
```

### 8.3 Privileged Clinical Audit Access Invariants

1. **Route:** `GET /api/v1/ai/audit/conversations/:id` (Dedicated route; standard `/conversations/:id` returns 404 for non-owners).
2. **Required Permission:** User must have role `Owner` OR permission `reports.read`.
3. **Mandatory Header:** `X-Audit-Reason: <string>` (Minimum 10 characters justifying access).
4. **Synchronous Audit Persistence:** The audit log event MUST be published and committed **before** conversation data is returned:
   ```typescript
   await this.auditPublisher.publish({
     tenantId: user.tenantId,
     userId: user.id,
     category: AuditEventCategory.DATA_ACCESS,
     eventType: AuditEventType.CLINICAL_CONVERSATION_INSPECTED,
     resourceType: 'ai_conversation',
     resourceId: conversationId,
     severity: AuditSeverity.HIGH,
     metadata: {
       targetUserId: conversation.userId,
       justification: auditReason,
       accessTimestamp: new Date().toISOString(),
     },
   });
   ```
   _Fail-Closed Guarantee:_ If audit publishing fails, the request throws `500 Internal Server Error` and data is **never** returned.

#### Disconnect & Recovery Protocol

1. Client loses connection while assistant message is `STREAMING`.
2. Frontend lifecycle transitions locally to `INTERRUPTED`.
3. When connectivity restores, client calls `GET /api/v1/ai/conversations/:id/generation-status`.
4. If backend generation completed successfully before disconnect: status returns `COMPLETED` with `canonicalMessageId`. Frontend fetches `/messages` and updates UI to `COMPLETED`.
5. If backend generation was interrupted: status returns `INTERRUPTED` with `retryAllowed: true`. Frontend renders partial text and enables the `Reintentar` action.
