## 1. Executive Summary

This deliverable establishes the application-layer architectural foundation for persistent AI conversations within `packages/core/src/ai/application/`. Building upon the domain entities and repository ports established in BE.03, this foundation defines:

1. **Transaction Execution Abstraction (`IAiConversationTransactionRunner`):** An application-facing Unit of Work port that allows multi-repository operations (conversation, turn, message, audit) to execute within an atomic transaction without coupling use cases to Prisma or database transaction primitives.
2. **Server-Side Prisma Transaction Runner (`PrismaAiConversationTransactionRunner`):** A concrete implementation residing strictly in `packages/core/src/ai/infrastructure/persistence/prisma/` (exported via `packages/core/server`) that wraps interactive `prisma.$transaction` calls and delegates to `.withTransaction(tx)`-scoped repository adapters.
3. **Application Input and Output Contracts (DTOs):** Strongly typed request and response specifications for subsequent BE.04 use cases, including Create Conversation with Initial Turn, Reserve Subsequent Turn, Get Conversation Details, List Conversations, Retrieve Message History, Update Title, and Persist Message State.
4. **Application Error Taxonomy:** A typed hierarchy of application errors rooted in `AiConversationApplicationError`, featuring machine-readable error codes and safe diagnostic details that never expose raw clinical or user prompt text.
5. **Functional Application Result Container (`AiApplicationResult`):** A type-safe, immutable success/failure container that permits expressive domain use-case results without throwing exceptions for normal control flow.
6. **Strict Monorepo & Architectural Boundary Compliance:** Zero `any` types, zero Prisma or NestJS dependencies in application layer contracts, and clean packaging where browser-safe contracts reside in `packages/core` root and server-only persistence adapters reside in `packages/core/server`.

## 3. Transaction Execution Abstraction

### 3.1 Port Contract (`IAiConversationTransactionRunner`)

Application use cases require atomic guarantees when coordinating state across conversations, turns, messages, and audit logs. The application port exposes:

```typescript
export const AI_CONVERSATION_TRANSACTION_RUNNER = Symbol('IAiConversationTransactionRunner');

export interface ConversationTransactionalRepositories {
  readonly conversationRepo: IAiConversationRepositoryPort;
  readonly turnRepo: IAiConversationTurnRepositoryPort;
  readonly messageRepo: IAiConversationMessageRepositoryPort;
  readonly auditRepo: IAiConversationAuditRepositoryPort;
}

export interface IAiConversationTransactionRunner {
  runInTransaction<T>(
    work: (repos: ConversationTransactionalRepositories) => Promise<T>,
  ): Promise<T>;
}
```

### 3.2 Concrete Prisma Runner (`PrismaAiConversationTransactionRunner`)

The server-side adapter implements `runInTransaction` using Prisma interactive transactions:

- Calls `this.prisma.$transaction(async (tx) => ...)`.
- Creates scoped instances of `PrismaAiConversationRepository`, `PrismaAiConversationTurnRepository`, `PrismaAiConversationMessageRepository`, and `PrismaAiConversationAuditRepository` using their `.withTransaction(tx)` factory methods.
- Invokes the application callback with the scoped repositories.
- If an unhandled infrastructure error occurs during commit, translates it into `TransactionFailureError`.
- If an `AiConversationApplicationError` is thrown, preserves and propagates the application error directly to trigger atomic rollback without double-wrapping.

## 4. Application Error Taxonomy

The application error hierarchy provides clear, machine-readable failure semantics:

| Error Class                               | Error Code                          | Description                                       | Safe Details                                   |
| :---------------------------------------- | :---------------------------------- | :------------------------------------------------ | :--------------------------------------------- |
| `AiConversationApplicationError`          | —                                   | Abstract base error class extending `Error`       | `code`, `details`                              |
| `ConversationNotFoundError`               | `AI_CONVERSATION_NOT_FOUND`         | Conversation not found or tenant mismatch         | `conversationId`                               |
| `TurnNotFoundError`                       | `AI_TURN_NOT_FOUND`                 | Turn not found or turn number missing             | `turnId`, `turnNumber`                         |
| `MessageNotFoundError`                    | `AI_MESSAGE_NOT_FOUND`              | Message not found                                 | `messageId`, `turnId`                          |
| `TenantOwnershipViolationError`           | `AI_TENANT_OWNERSHIP_VIOLATION`     | Attempted cross-tenant data access                | `entityType`, `entityId`                       |
| `DuplicateClientTurnPayloadMismatchError` | `AI_CLIENT_TURN_PAYLOAD_MISMATCH`   | Idempotent key reused with mismatched hash        | `clientTurnId`, `existingHash`, `providedHash` |
| `TurnAlreadyInProgressError`              | `AI_TURN_ALREADY_IN_PROGRESS`       | Concurrent generation on active conversation turn | `conversationId`, `activeTurnId`               |
| `InvalidConversationLifecycleError`       | `AI_INVALID_CONVERSATION_LIFECYCLE` | Invalid operation for current conversation state  | `conversationId`, `reason`                     |
| `InvalidMessageOperationError`            | `AI_INVALID_MESSAGE_OPERATION`      | Invalid message transition or update              | `messageId`, `reason`                          |
| `PersistenceConflictError`                | `AI_PERSISTENCE_CONFLICT`           | Concurrency race or sequence collision            | `operation`, `reason`                          |
| `TransactionFailureError`                 | `AI_TRANSACTION_FAILURE`            | Unhandled transaction failure during execution    | `operation`, `originalError`                   |

## 5. Application Contracts (DTOs)

The following strongly typed contracts were defined in `packages/core/src/ai/application/dtos/ai-conversation.dtos.ts`:

1. **`CreateConversationWithInitialTurnInput` / `CreateConversationWithInitialTurnResult`:**
   - Conversation creation coupled with initial user message and turn sequence #1 reservation.
2. **`ReserveSubsequentTurnInput` / `ReserveSubsequentTurnResult`:**
   - Atomic reservation of subsequent turn sequences (`turnNumber = N + 1`), handling idempotent client tokens.
3. **`GetConversationInput` / `ConversationDetailDto`:**
   - Retrieval of conversation metadata, active turn state, and turn counts.
4. **`ListConversationsInput` / `ListConversationsResult`:**
   - Keyset-paginated conversation listing filtered by tenant and optional user/status.
5. **`GetMessageHistoryInput` / `MessageHistoryResultDto`:**
   - Keyset-paginated message retrieval ordered by turn sequence and chronological order.
6. **`UpdateConversationTitleInput` / `UpdateConversationTitleResult`:**
   - Updating conversation display title with validation.
7. **`PersistMessageStateInput` / `PersistMessageStateResult`:**
   - Updating generation status, completion timestamps, and canonical flags.

## 6. Functional Result Container

To avoid exception-based control flow for expected business outcomes, `AiApplicationResult<T, E>` was implemented:

- `AiApplicationResult.ok<T, E>(value)`
- `AiApplicationResult.fail<T, E>(error)`
- Methods `.getValue()`, `.getError()`, properties `.isSuccess`, `.isFailure`.
- Exported as `AiApplicationResult` from root package to avoid collision with `packages/core/src/scheduling`'s `ApplicationResult`.
