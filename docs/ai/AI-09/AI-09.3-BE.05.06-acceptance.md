## 3. DTO and Validation Summary

Request validation is executed through the global NestJS `ValidationPipe` with `transform: true, whitelist: true, forbidNonWhitelisted: true`.

### Validated Input Contracts:

1. **User Prompt Validation:** Enforces `@IsString()`, `@IsNotBlank()`, and `@MaxLength(4000)`. Whitespace-only prompts (spaces, newlines, tabs) are rejected immediately with `400 Bad Request`.
2. **Client-Stable Turn Identifiers (`clientTurnId`):** Enforces `@IsString()`, `@IsNotBlank()`, and length 1..64 characters.
3. **Conversation Title:** Enforces `@IsString()`, `@IsNotBlank()`, and length 1..255 characters.
4. **Pagination Bounds:**
   - Conversation List Limit: 1..100 (default 20).
   - Message History Limit: 1..100 (default 20).
5. **Cursor Validation:**
   - Conversation List Cursor (`@IsValidConversationListCursor`): Enforces valid base64url encoding of `{ d: ISO8601, id: conversationId }`.
   - Message History Cursor (`@IsValidMessageHistoryCursor`): Enforces valid base64url encoding of `{ s: sequenceNumber, id: messageId }`. Rejects activity timestamp cursors.
6. **Mass-Assignment Defense:** Any unwhitelisted properties in request payloads (e.g., `tenantId`, `userId`, `role`, `status`, `isCanonical`, `turnIndex`, `payloadHash`) cause instant rejection with `400 Bad Request`.
7. **Response DTO Sanitization:** Zero internal database fields (Prisma models, database foreign keys, table metadata) are exposed.

## 4. Authentication and Authorization Evidence

1. **Guard Coverage:** `@UseGuards(AuthenticationGuard, AuthorizationGuard)` is attached to `AiConversationController` at the class level.
2. **Context Resolution:** [@TrustedAi()](file:///c:/Projects/kinergy-platform/apps/api/src/ai/conversation/decorators/trusted-ai-context.decorator.ts) extracts `actorId`, `tenantId`, `roles`, and `permissions` exclusively from verified cryptographically signed authentication context (`request.user`).
3. **Tenant Spoofing Rejection:** Client-supplied tenant identifiers in headers, URL queries, or request bodies are ignored or rejected by validation.
4. **Privileged Inspection RBAC:**
   - Evaluated by `AuthorizationGuard` via `@Roles('Owner')` and `@RequirePermissions(PERMISSIONS.AI.CONVERSATIONS_AUDIT)`.
   - Standard roles (`Physiotherapist`, `Trainer`, `Receptionist`, `Doctor`) receive `403 Forbidden`.
   - Authorized `Owner` calls succeed only when accompanied by a justification `reason` ($\ge 10$ characters).
   - Zero new unsupported permissions were introduced; reuses catalog permission `'ai.conversations.audit'`.

## 5. Tenant Isolation & Anti-Enumeration Defense

1. **Scoped Persistence Queries:** All repository and use case calls are scoped by `tenantId`.
2. **404 Anti-Enumeration Behavior:**
   - When Tenant B queries or mutates an ID owned by Tenant A, the repository returns `null` or raises [ConversationNotFoundError](file:///c:/Projects/kinergy-platform/packages/core/src/ai/application/errors/ai-conversation-application.error.ts).
   - [AiConversationExceptionFilter](file:///c:/Projects/kinergy-platform/apps/api/src/ai/conversation/filters/ai-conversation-exception.filter.ts) translates this to `404 Not Found`.
   - Tenant B is never informed whether Tenant A's conversation exists (`403` is never returned for cross-tenant resource queries).

## 6. Idempotency & Concurrency Invariants

Verified against actual PostgreSQL transactions:

1. **Identical Client Turn Replay:** Same `clientTurnId` and matching prompt payload recovers the existing turn with `isIdempotentReplay: true` and `idempotencyOutcome: 'EXISTING_RECOVERED'`.
2. **Payload Conflict Detection:** Same `clientTurnId` with conflicting prompt or title raises `DuplicateClientTurnPayloadMismatchError` translated to `409 Conflict`.
3. **Single Generation Concurrency Invariant:** Attempting to reserve a new turn while a previous turn is in progress (`PENDING`) triggers `TurnAlreadyInProgressError` mapped to `409 Conflict` with a `Retry-After: 2` header.

---

## 7. Message History & Keyset Pagination

1. **Ordering Invariant:** Canonical message history is ordered monotonically by sequence number (`sequenceNumber ASC`).
2. **Cursor Continuity:** Uses immutable sequence-based cursor `{ s: sequenceNumber, id: messageId }`.
3. **Multi-Page Navigation:** Verified against PostgreSQL that page 1 (`limit: 1`) and page 2 (`limit: 1, cursor: page1.nextCursor`) yield distinct sequential messages with zero duplicate records across pages.
4. **Canonical Read Model:** Non-canonical in-progress assistant placeholders are excluded from standard history until completion.

## 9. End-to-End Workflow Acceptance Results

Executed against PostgreSQL database with real relational constraints:

### Workflow A — Initial Conversation Creation & Idempotency

1. User authenticated in Tenant Alpha.
2. `POST /api/v1/ai/conversations` creates conversation, initial turn (index 1), user message (seq 1), and assistant placeholder (seq 2) atomically in a single PostgreSQL transaction.
3. Replaying the identical request recovers the existing turn (`isIdempotentReplay: true`).
4. Replaying with mismatched prompt returns `409 Conflict`.

- **Verdict:** `PASS`

### Workflow B — Subsequent Turn Reservation & Conflict Handling

1. Conversation retrieved via `GET /api/v1/ai/conversations/:id`.
2. `POST /api/v1/ai/conversations/:id/turns` reserves turn 2 with monotonic index 2.
3. Attempting to reserve turn 3 while turn 2 is active returns `409 Conflict` (`TurnAlreadyInProgressError`) with `Retry-After: 2`.
4. Marking turn 2 completed allows subsequent turn reservation.
5. Replaying turn 2 with identical payload recovers turn 2 idempotently.

- **Verdict:** `PASS`

### Workflow C — Conversation History & Keyset Pagination

1. `GET /api/v1/ai/conversations` lists conversations for user with limit 20.
2. `GET /api/v1/ai/conversations/:id` returns aggregate details and child turns.
3. `GET /api/v1/ai/conversations/:id/messages?limit=1` returns page 1 (`sequenceNumber: 1`, `hasMore: true`).
4. `GET /api/v1/ai/conversations/:id/messages?limit=1&cursor=<nextCursor>` returns page 2 (`sequenceNumber: 2`, `hasMore: false`).
5. Verified monotonic ordering (`page1.seq < page2.seq`) and zero duplicate messages between pages.

- **Verdict:** `PASS`

### Workflow D — Tenant Isolation & Anti-Enumeration

1. Tenant Alpha creates conversation `conv_alpha_001`.
2. User in Tenant Beta attempts:
   - `GET /api/v1/ai/conversations/conv_alpha_001` -> `404 Not Found`
   - `PATCH /api/v1/ai/conversations/conv_alpha_001/title` -> `404 Not Found`
   - `POST /api/v1/ai/conversations/conv_alpha_001/turns` -> `404 Not Found`
   - `GET /api/v1/ai/conversations/conv_alpha_001/messages` -> `404 Not Found`
   - `POST /api/v1/ai/conversations/conv_alpha_001/audit-inspect` -> `404 Not Found`
3. Verified zero cross-tenant data leakage or existence confirmation.

- **Verdict:** `PASS`

### Workflow E — Privileged Inspection & Fail-Closed Audit Logging

1. User with non-Owner role (`Doctor`, `Trainer`) attempts `POST /:id/audit-inspect` -> rejected with `403 Forbidden` (`TenantOwnershipViolationError`); zero audit logs committed.
2. Authorized `Owner` with `ai.conversations.audit` inspects conversation with valid reason -> audit log committed to `ai_conversation_audit_logs` and conversation details returned.
3. When audit repository persistence fails, use case throws `TransactionFailureError` (500) and **zero** conversation content or messages are leaked to the caller.

- **Verdict:** `PASS`
