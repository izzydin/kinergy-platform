## 1. Executive Summary

The objective of milestone **FE.01.01** is to establish the authoritative, evidence-backed frontend integration contract derived directly from the implemented and verified **AI-09.3** backend (`AiConversationController`, application use cases, DTOs, and PostgreSQL persistence layer).

In earlier iterations (AI-09.2), frontend chat operations relied on stateless RAG invocations (`POST /api/v1/ai/knowledge/query`) and client-side partitioned local storage (`assistant-storage.service.ts`). With the completion of backend milestone **BE.07** ([AI-09.3-BE.07.07-final-acceptance.md](file:///c:/Projects/kinergy-platform/docs/ai/AI-09/AI-09.3-BE.07.07-final-acceptance.md)), the backend provides a fully transactional, durable, multitenant conversation persistence and turn execution lifecycle in PostgreSQL.

This document maps the real backend REST endpoints, serialization DTOs, keyset pagination algorithms, client-stable idempotency mechanics, error responses, and status semantics into the existing frontend architecture without introducing architecture drift, client-side persistence substitutes, or unsupported endpoint assumptions.

## 4. Status Semantics & FSM Mapping

### 4.1 Backend Status Vocabulary vs. Frontend Generation FSM

The frontend generation state machine (`apps/web/src/modules/intelligence/assistant/types/generation.types.ts`) defines seven lifecycle states:

```typescript
export type GenerationStatus =
  'IDLE' | 'PENDING' | 'STREAMING' | 'COMPLETED' | 'FAILED' | 'CANCELLED' | 'INTERRUPTED';
```

The backend maintains two distinct status enums:

1. **TurnStatus** (`AiConversationTurn.status`): `'PENDING' | 'STREAMING' | 'COMPLETED' | 'FAILED' | 'CANCELLED' | 'INTERRUPTED'`
2. **GenerationStatus** (`AiConversationMessage.status`): `'PENDING' | 'STREAMING' | 'SUCCESS' | 'FAILED' | 'CANCELLED' | 'INTERRUPTED'`

> [!IMPORTANT]
> **Status Vocabulary Distinction:**  
> The backend Assistant Message status uses **`SUCCESS`**, whereas TurnStatus and the frontend FSM use **`COMPLETED`**.  
> The frontend must map message `status === 'SUCCESS'` to generation FSM `COMPLETED`.  
> There is **NO `RECOVERING` status** in either backend or frontend.

### 4.2 State Machine Translation Matrix

| Event / Lifecycle Stage           | Backend TurnStatus                          | Backend Assistant Message Status | Frontend Generation FSM State                                                                                                                                  | Action / UI Interpretation                                                                      |
| :-------------------------------- | :------------------------------------------ | :------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------- | :---------------------------------------------------------------------------------------------- |
| **Initial / Composer Ready**      | — _(No active turn)_                        | —                                | `IDLE`                                                                                                                                                         | Input composer enabled; waiting for user submission.                                            |
| **Turn Reserved (`201 Created`)** | `PENDING`                                   | `PENDING`                        | `PENDING`                                                                                                                                                      | Render user prompt immediately; show pulsing assistant placeholder indicator; disable composer. |
| **Streaming First Chunk**         | `STREAMING`                                 | `STREAMING`                      | `STREAMING`                                                                                                                                                    | Begin incremental text rendering; display stop/cancel button.                                   |
| **Terminal Completion**           | `COMPLETED`                                 | `SUCCESS`                        | `COMPLETED`                                                                                                                                                    | Render final content; render verified citations; re-enable composer.                            |
| **Terminal Failure**              | `FAILED`                                    | `FAILED`                         | `FAILED`                                                                                                                                                       | Render error banner with retry option; keep prompt draft available.                             |
| **User Cancellation**             | `CANCELLED`                                 | `CANCELLED`                      | `CANCELLED`                                                                                                                                                    | Abort network stream; mark turn cancelled; re-enable composer.                                  |

## 5. Pagination & Ordering Semantics

The backend implements deterministic **Keyset (Cursor-based) Pagination** for both conversation lists and message histories. Offset/limit (`SKIP`/`TAKE`) pagination is strictly rejected to prevent quadratic scanning degradation and pagination drift.

### 5.1 Conversation List Pagination (`GET /api/v1/ai/conversations`)

- **Ordering Guarantee:** Deterministic order by `(lastActivityAt DESC, id DESC)`.
- **Cursor Representation:** URL-safe Base64 encoded JSON string (`ConversationListCursor`):
  ```json
  { "a": "2026-11-24T14:00:00.000Z", "id": "conv_01934f8a-..." }
  ```
- **Page Size Limits:** Default `20`, Minimum `1`, Maximum `100`.
- **Query Parameters:**
  - `cursor`: string (optional, Base64URL cursor from previous `nextCursor`).
  - `limit`: number (optional, integer 1-100).
  - `includeArchived`: boolean (optional, default `false`).
- **Empty Page Representation:** `{ items: [], nextCursor: null, hasMore: false }`.
- **Consistency Warning:**  
  Because `lastActivityAt` is updated whenever a conversation receives a new turn, conversation list pagination does **NOT** guarantee snapshot consistency. If a conversation receives new activity while the user scrolls, that conversation moves to the top and may reappear on subsequent pages. The frontend TanStack Query cache must deduplicate items by `id`.

### 5.2 Canonical Message History Pagination (`GET /api/v1/ai/conversations/:id/messages`)

- **Ordering Guarantee:** Strictly monotonic ascending order by `(sequenceNumber ASC, id ASC)`.
- **Cursor Representation:** URL-safe Base64 encoded JSON string (`MessageHistoryCursor`):
  ```json
  { "s": 4, "id": "msg_01934f8a-..." }
  ```
  _(Encodes integer `s` = sequenceNumber, `id` = messageId)._
- **Page Size Limits:** Default `20`, Minimum `1`, Maximum `100`.
- **Query Parameters:**
  - `cursor`: string (optional sequence cursor).
  - `limit`: number (optional integer 1-100).
- **Empty Page Representation:** `{ messages: [], nextCursor: null, hasMore: false }`.
- **Consistency Guarantee:**  
  Because `sequenceNumber` is immutable and monotonic, message history pagination is **strictly snapshot-consistent**.
- **Prohibition:**  
  The frontend must **NEVER** use `createdAt` or `lastActivityAt` timestamps as message history cursors.

## 6. Idempotency & Conflict Semantics

The backend implements client-stable turn idempotency (`AiPayloadHasher` + PostgreSQL uniqueness).

### 6.1 `clientTurnId` Rules

1. **Origin:** The client generates `clientTurnId` before issuing `POST /api/v1/ai/conversations` or `POST /api/v1/ai/conversations/:id/turns`.
2. **Format:** Standard UUID v4 (e.g. `crypto.randomUUID()`) or unique client key, maximum 64 characters.
3. **Stability:** The `clientTurnId` **must remain identical** across all network retries, timeout recoveries, or offline reconciliations for the same prompt submission. The frontend must **never** generate a new `clientTurnId` when retrying a failed HTTP request.

### 6.2 Backend Payload Hash Comparison

The backend computes a SHA-256 hash over a normalized canonical representation:

- `prompt`: Trimmed of leading/trailing whitespace, with CRLF (`\r\n`) normalized to LF (`\n`).
- `metadata`: Object keys sorted lexicographically at all recursive levels (if present).
- _Excluded:_ Request headers, timestamps, user/tenant identifiers, and `clientTurnId`.

### 6.3 Behavior Matrix

| Client Request Scenario                                     | Backend Action                                                                       | Response Status           | Response Body Properties                                                                     | Frontend Handling                                                      |
| :---------------------------------------------------------- | :----------------------------------------------------------------------------------- | :------------------------ | :------------------------------------------------------------------------------------------- | :--------------------------------------------------------------------- |
| **Initial Turn Submission**                                 | Inserts turn & initial messages in PostgreSQL, dispatches worker.                    | `201 Created`             | `isIdempotentReplay: false`<br>`idempotencyOutcome: "CREATED"`                               | Transition to `PENDING`; render placeholder.                           |
| **Network Retry: Same `clientTurnId` + Same Payload**       | Reclaims existing logical turn; suppresses duplicate background generation.          | `201 Created`             | `isIdempotentReplay: true`<br>`idempotencyOutcome: "EXISTING_RECOVERED"`                     | Treat as successful reservation; reconcile state without resetting UI. |
| **Conflicting Retry: Same `clientTurnId` + Altered Prompt** | Rejects conflicting payload hash (`DuplicateClientTurnPayloadMismatchError`).        | `409 Conflict`            | `code: "AI_CONFLICT"`<br>`message: "clientTurnId ... already exists with different payload"` | Generate a fresh `clientTurnId` for the altered prompt.                |
| **Concurrent Submission While Turn In-Flight**              | Rejects second turn reservation on same conversation (`TurnAlreadyInProgressError`). | `409 Conflict`            | `code: "AI_CONFLICT"`<br>Header: `Retry-After: 2`                                            | Show "Generation in progress" warning; wait 2s before retry.           |
| **Replay of Completed Turn**                                | Returns existing completed turn summary.                                             | `201 Created`             | `isIdempotentReplay: true`<br>`turnStatus: "COMPLETED"`                                      | Hydrate completed state; do not trigger new generation.                |
| **Transient Database Lock Contention**                      | Database transaction deadlock during high concurrency retry.                         | `503 Service Unavailable` | `code: "AI_TRANSIENT_TRANSACTION_FAILURE"`<br>Header: `Retry-After: 1`                       | Automatically retry after 1 second using the same `clientTurnId`.      |

## 7. Authentication, Tenant & Ownership Assumptions

1. **Authentication Transport:**  
   Supplied via standard `Authorization: Bearer <token>` header on every request. Handled automatically by the frontend HTTP client transport (`apps/web/src/shared/api/http-client.ts`).
2. **Session Refresh:**  
   Handled transparently by the existing frontend authentication interceptor pipeline using Refresh Token Rotation (RTR).
3. **Tenant & Actor Derivation:**  
   The backend **strictly discards or forbids** client-provided `tenantId` or `userId` in request bodies. Identity is derived on the server from the verified JWT principal (`TrustedAiContext`).
4. **Ownership Model:**
   - **Cross-Tenant:** Strictly isolated. Cross-tenant queries return `404 Not Found` (never `403`), concealing the existence of the conversation.
   - **Same-Tenant:** Collaborative. Any authorized user within the tenant can view and append turns to active conversations within that tenant.
   - **Privileged Inspection:** Restricted to `Owner` role with `ai.conversations.audit` permission. Requires $\ge 10$ character reason and fails closed if the PostgreSQL audit log write fails.
