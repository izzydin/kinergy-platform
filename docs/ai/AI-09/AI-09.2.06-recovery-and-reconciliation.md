# AI-09.2.06 — Generation Cancellation, Recovery & Canonical Response Reconciliation

## 1. Executive Summary

Milestone **AI-09.2.06** establishes robust frontend request resilience, truthful cancellation semantics, reliable connection interruption handling, and authoritative backend state reconciliation for the **Kynergy Intelligence AI Assistant**.

Distributed LLM generation interfaces face inherent uncertainties: network drops, reverse proxy timeouts (HTTP 502/503/504), client navigation teardown, and transport disconnections while the backend or upstream inference engines continue running. This implementation adheres strictly to the architectural principle that **the backend remains the sole source of truth**, avoiding speculative client simulations, false guarantees, and silent message deletions.

---

## 2. Cancellation Architecture & Semantics

### 2.1 Backend Capability Verification

An inspection of the backend controllers and services (`AiRAGController` at `apps/api/src/modules/ai/rag/controllers/ai-rag.controller.ts` and `RAGOrchestratorService` at `apps/api/src/modules/ai/rag/services/rag-orchestrator.service.ts`) confirmed:

- **Supported Mechanism:** Transport-level cancellation via `AbortSignal` passed through HTTP request handling. The backend detects client socket closure, catching `GenerationCancelledException`.
- **Unsupported Mechanism:** There is **no dedicated REST endpoint** (e.g., `POST /api/ai/conversations/:id/cancel` or protocol message) for out-of-band asynchronous task cancellation.

### 2.2 Truthful Client-Side Semantics

Because transport termination does not prove that upstream remote inference providers (e.g., external LLM APIs) halted immediately, the frontend implements **truthful cancellation semantics**:

- When the user clicks the explicit **"Detener generación"** action, the client's `AbortController` triggers `signal.abort()`.
- The assistant placeholder message is immediately transitioned to `status: 'cancelled'`.
- The stored error message honestly states:
  > _"Generación detenida en el cliente (conexión cerrada). La respuesta no pudo ser completada."_
- The UI never asserts that the remote LLM process ceased computing; it explicitly records that client-side reception was terminated.

### 2.3 Cross-Conversation Protection

- The `cancelGeneration(targetConversationId?: string)` method guards against race conditions where a user switches conversations while a request is in flight.
- If a cancellation request targets a conversation ID different from the active submission ID, the active `AbortController` is protected and continues undisturbed.

## 3. Connection Interruption Handling & State Preservation

When network drops or gateway timeouts occur, the frontend guarantees complete data integrity:

### 3.1 Interruption Classification

In `use-generation-lifecycle.ts`, the error handler analyzes normalized `ApiError` instances:

- **Network Disconnects:** Detected via `!navigator.onLine`, `error.statusCode === 0`, or error messages matching `failed to fetch`, `networkerror`, or `network request failed`.
- **Gateway Timeouts:** Detected via `error.statusCode === 504`, `502`, `503`, or code `PROVIDER_TIMEOUT`.

### 3.2 Integrity Invariants

- **User Prompt Preservation:** The user's input prompt is **never** deleted or reverted upon failure. It remains committed to the active conversation history.
- **Message Identity Stability:** The original `assistantMessageId` and `userMessageId` assigned during optimistic dispatch remain invariant.
- **Partial Content Retention:** Any text or tokens accumulated prior to the failure are retained in the message entity rather than wiped.
- **Explicit Status Flag:** The assistant turn is marked with `status: 'interrupted'` (or `'error'` for business/validation errors) rather than `'completed'`.
- **Unmount Teardown:** If the chat workspace or page is unmounted during generation, the `useEffect` cleanup hook immediately triggers `controller.abort()`, synchronizes the persistent storage to mark the pending turn as `interrupted`, and prevents hanging loading spinners.

---

## 4. Recovery & Manual Retry Architecture

To uphold clinical accuracy and user intent, automatic background resubmission is strictly avoided:

- **No Automatic Retries:** Automatic retries of complex LLM queries risk executing duplicate or conflicting inferences and corrupting state.
- **Explicit User Action:** When a turn is marked `'cancelled'`, `'interrupted'`, or `'error'`, a dedicated `MessageStatusIndicator` renders an action button (`Reintentar`) alongside an explanatory banner and icon (`Ban` for cancelled, `WifiOff` for interrupted, `AlertCircle` for error).
- **Composer & Message Action Trigger:** Clicking `Reintentar` on a failed assistant turn or user message re-populates and resubmits the original prompt via `useGenerationLifecycle`, initiating a fresh turn with clean telemetry.

## 5. Authoritative Canonical Response Reconciliation

When the backend completes answer synthesis, the frontend reconciles the state through authoritative replacement:

```mermaid
sequenceDiagram
    autonumber
    actor User as User / Clinician
    participant UI as ChatWorkspace / Composer
    participant Hook as useGenerationLifecycle
    participant Storage as assistantStorageService
    participant Cache as TanStack Query Cache
    participant API as Backend AI RAG API

    User->>UI: Submit clinical query
    UI->>Hook: submitMessage(prompt)
    Hook->>Storage: Append User Msg (success) + Asst Placeholder (pending)
    Hook->>Cache: setQueryData(active conversation)
    Hook->>API: queryKnowledge(prompt, signal)

    alt Successful Response
        API-->>Hook: RAGAnswerResponseDto (canonical answer, sources, metadata)
        Hook->>Storage: updateMessage(assistantMessageId, canonical)
        Note over Hook,Storage: Preserves original createdAt timestamp; applies citations & telemetry
        Hook->>Cache: setQueryData(authoritative conversation)
        Hook->>Cache: setQueryData(conversation summaries)
        Hook->>UI: Transition to COMPLETED
    else User Clicks Stop
        User->>UI: Click "Detener generación"
        UI->>Hook: cancelGeneration(convId)
        Hook->>API: AbortController.abort()
        Hook->>Storage: updateMessage(asstId, status: 'cancelled')
        Hook->>Cache: setQueryData(cancelled conversation)
        Hook->>UI: Transition to CANCELLED
    else Network Loss / 504 Timeout
        API-->>Hook: NetworkError / 504 Gateway Timeout
        Hook->>Storage: updateMessage(asstId, status: 'interrupted')
        Hook->>Cache: setQueryData(interrupted conversation)
        Hook->>UI: Transition to INTERRUPTED (with Retry action)
    end
```

### Key Reconciliation Rules:

1. **Timestamp Preservation:** The assistant message's original chronological `createdAt` timestamp is strictly preserved during replacement, ensuring conversation timeline consistency.
2. **Authoritative Citation Binding:** The backend `RAGAnswerResponseDto.sources` array is bound directly to the message's `sources` property, guaranteeing verifiable clinical attribution.
3. **Telemetry Binding:** The backend `metadata` (`latencyMs`, `model`, `retrievalCount`) is persisted into `message.metadata` without modification.
4. **Cache & Storage Synchronization:** Storage (`localStorage` with in-memory fallback) and TanStack Query cache (`aiAssistantKeys.conversation(...)` and `aiAssistantKeys.conversations(...)`) are updated synchronously, preventing UI flicker or out-of-order rendering.
