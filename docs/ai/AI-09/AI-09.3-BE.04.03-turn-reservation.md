## 1. Executive Summary

This report documents the architectural design, implementation, and live PostgreSQL verification of `ReserveConversationTurnUseCase` in `packages/core/src/ai/application/use-cases/reserve-conversation-turn.use-case.ts`.

The use case coordinates subsequent conversation turn reservations under strict multi-tenant boundaries, atomic aggregate sequence allocation, cryptographic request idempotency, and concurrency arbitration:

1. **Atomic Transaction Boundary:** Coordinates conversation verification, active generation checks, turn counter increment, message counter increments, turn creation, user message creation, and assistant placeholder creation within a single interactive transaction via `IAiConversationTransactionRunner`.
2. **One Active Generation Per Conversation Invariant:** Authoritatively enforced by both application checks (`findActiveTurn`) and PostgreSQL's partial unique index `ai_conversation_active_generation_idx` (`WHERE "role" = 'ASSISTANT' AND "status" IN ('PENDING', 'STREAMING')`). Competing reservations roll back completely with zero orphaned records, raising `TurnAlreadyInProgressError`.
3. **Idempotent Replay & Conflict Detection:**
   - Same `clientTurnId` + matching payload hash on an in-progress or terminal turn returns the existing persisted state (`isIdempotentReplay: true`, `idempotencyOutcome: 'EXISTING_RECOVERED'`) without creating new database rows.
   - Same `clientTurnId` + mismatched payload hash raises typed `DuplicateClientTurnPayloadMismatchError`.
4. **PostgreSQL Concurrency Arbitration:** Arbitrates concurrent duplicate requests with the same `clientTurnId` across independent database connections, recovering the committed turn upon unique constraint collision and returning `EXISTING_RECOVERED`.
5. **Monotonic Counter-Based Sequences:** Allocates monotonic `turnIndex` and `sequenceNumber` values directly from aggregate counters on `AiConversation`, strictly eliminating `MAX(sequence) + 1` races.

## 2. Transaction Workflow

```
Client Reservation Request
      │
      ▼
Input Validation (tenantId, userId, conversationId, clientTurnId, non-empty userPrompt)
      │
      ▼
Deterministic Payload Hashing (Canonical prompt + metadata -> SHA-256)
      │
      ▼
Preliminary Fast-Path Idempotency Check (turnRepo.findByClientTurnId)
 ├─ Found in current conversation & Matching Hash: Return EXISTING_RECOVERED
 ├─ Found in another conversation: Throw PersistenceConflictError
 ├─ Found with Mismatched Hash: Throw DuplicateClientTurnPayloadMismatchError
 └─ Not Found: Proceed to Transaction
      │
      ▼
Atomic Transaction Execution (txRunner.runInTransaction)
 ├─ Re-check clientTurnId within TX (guard against concurrent commit)
 ├─ Fetch Conversation (conversationRepo.findById)
 │   ├─ Not found: Throw ConversationNotFoundError
 │   ├─ Tenant/user mismatch: Throw TenantOwnershipViolationError
 │   └─ Archived/deleted: Throw InvalidConversationLifecycleError
 ├─ Enforce One-Active-Generation: turnRepo.findActiveTurn
 │   └─ Active turn exists (PENDING/STREAMING): Throw TurnAlreadyInProgressError
 ├─ Increment Aggregate Counters Monotonically:
 │   ├─ turnCounter -> turnIndex (e.g. 2)
 │   ├─ messageCounter -> userSeq (e.g. 3)
 │   ├─ messageCounter -> assistantSeq (e.g. 4)
 │   └─ conversation.recordActivity()
 ├─ Persist Updated Conversation (locks conversation row)
 ├─ Persist AiConversationTurn (turnIndex, PENDING, activeAttemptId: null)
 ├─ Persist AiConversationMessage (role USER, seq 3, status SUCCESS, content: prompt)
 ├─ Persist AiConversationMessage (role ASSISTANT, seq 4, status PENDING, content: '')
 ├─ Associate Active Attempt: turn.associateActiveAttempt(assistantMsg.id)
 ├─ Update Turn with Active Attempt Pointer
 └─ Return CREATED (isIdempotentReplay: false)
      │
      ▼ (On Unique Constraint Collision)
Catch Concurrency Violation
 ├─ Same clientTurnId Collision: Await winning commit, verify hash, return EXISTING_RECOVERED
 ├─ Active Generation Collision (ai_conversation_active_generation_idx): Throw TurnAlreadyInProgressError
 └─ Turn Index Collision (uq_conversation_turn_index): Throw TurnAlreadyInProgressError
```

## 3. Idempotency Behavior & Replay Contracts

| Scenario                          | Condition                                                        | Outcome                                                                                                          | Persisted State Impact                                                  |
| :-------------------------------- | :--------------------------------------------------------------- | :--------------------------------------------------------------------------------------------------------------- | :---------------------------------------------------------------------- |
| **New Reservation**               | `clientTurnId` not seen                                          | `isIdempotentReplay: false`<br>`idempotencyOutcome: 'CREATED'`                                                   | Inserts Turn, User Msg, Assistant Msg; increments conversation counters |
| **Idempotent In-Progress Replay** | Same `clientTurnId`, same payload, turn is `PENDING`/`STREAMING` | `isIdempotentReplay: true`<br>`idempotencyOutcome: 'EXISTING_RECOVERED'`<br>`turnStatus: PENDING` or `STREAMING` | No database writes; returns existing turn state                         |
| **Idempotent Terminal Replay**    | Same `clientTurnId`, same payload, turn is `COMPLETED`/`FAILED`  | `isIdempotentReplay: true`<br>`idempotencyOutcome: 'EXISTING_RECOVERED'`<br>`turnStatus: COMPLETED` or `FAILED`  | No database writes; returns existing terminal state                     |
| **Payload Hash Mismatch**         | Same `clientTurnId`, different prompt or metadata                | Throws `DuplicateClientTurnPayloadMismatchError`                                                                 | No database writes; existing turn remains untouched                     |
| **Concurrent Same-Key Race**      | Two simultaneous requests with same `clientTurnId`               | Winner: `'CREATED'`<br>Loser: recovers and returns `'EXISTING_RECOVERED'`                                        | Exactly 1 turn and 2 messages created in PostgreSQL                     |
| **Cross-Conversation Key Reuse**  | `clientTurnId` exists in different conversation                  | Throws `PersistenceConflictError`                                                                                | Request rejected                                                        |

## 4. Active Generation Enforcement

- **Application Invariant Check:**
  `turnRepo.findActiveTurn(tenantId, conversationId)` checks for turns in `status IN ('PENDING', 'STREAMING')`. If found, immediately throws `TurnAlreadyInProgressError(conversationId, activeTurn.id.value)` without initiating message creation.
- **Database Authoritative Partial Unique Index:**
  ```sql
  CREATE UNIQUE INDEX "ai_conversation_active_generation_idx"
      ON "ai_conversation_messages"("conversation_id")
      WHERE "role" = 'ASSISTANT' AND "status" IN ('PENDING', 'STREAMING');
  ```
  If two competing requests bypass the preliminary application check simultaneously, PostgreSQL enforces this partial unique index at row insertion. The losing transaction aborts and rolls back completely, ensuring **zero orphaned user messages or turns**.

## 5. Sequence Allocation Strategy

- **Aggregate Monotonic Counters:**
  The `AiConversation` aggregate maintains:
  - `turnCounter: Int` (starts at 0 on conversation creation, incremented to 1 for initial turn, 2 for second turn, etc.).
  - `messageCounter: Int` (starts at 0, incremented to 1 for user msg 1, 2 for assistant msg 1, 3 for user msg 2, 4 for assistant msg 2, etc.).
- **Row-Level Serialization:**
  Updating `AiConversation` within `this.txRunner.runInTransaction` issues a `SELECT ... FOR UPDATE` / row lock on the conversation row in PostgreSQL, serializing sequence counter increments and guaranteeing duplicate-free monotonic sequence numbers without `MAX(sequence) + 1`.
