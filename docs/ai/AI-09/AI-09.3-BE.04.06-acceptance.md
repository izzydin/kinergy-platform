## 3. Transaction Boundaries & Atomicity

### 3.1 Interactive Transaction Orchestration

All multi-record writes are orchestrated by `IAiConversationTransactionRunner` ([ai-conversation-transaction-runner.port.ts](file:///c:/Projects/kinergy-platform/packages/core/src/ai/application/ports/ai-conversation-transaction-runner.port.ts)):

1. In `CreateConversationWithInitialTurnUseCase`:
   - An interactive PostgreSQL transaction creates:
     1. `AiConversation` (initial turnCounter = 1, messageCounter = 2).
     2. `AiConversationTurn` (turnIndex = 1, status = PENDING).
     3. `AiConversationMessage` (role = USER, sequenceNumber = 1, status = SUCCESS).
     4. `AiConversationMessage` (role = ASSISTANT, sequenceNumber = 2, status = PENDING).
     5. Updates `AiConversationTurn` with `activeAttemptId = assistantMessage.id`.
2. In `ReserveConversationTurnUseCase`:
   - Locks the conversation row via atomic increment.
   - Creates:
     1. `AiConversationTurn` (turnIndex = N, status = PENDING).
     2. `AiConversationMessage` (role = USER, sequenceNumber = M, status = SUCCESS).
     3. `AiConversationMessage` (role = ASSISTANT, sequenceNumber = M + 1, status = PENDING).
     4. Updates `AiConversationTurn` with `activeAttemptId = assistantMessage.id`.

### 3.2 Rollback Verification

Integration tests in `transactional-consistency.integration.spec.ts` injected mid-transaction aborts (after conversation insertion, before turn creation). Verified in PostgreSQL:

- **0 rows persisted** in `ai_conversations`.

- **0 rows persisted** in `ai_conversation_messages`.

## 4. Idempotency & Concurrency Arbitration

### 4.1 Cryptographic Determinism

- **Payload Hasher:** SHA-256 computation over trimmed user prompt and canonicalized metadata (`AiPayloadHasher`).
- **Stable Identifiers:** `clientTurnId` is strictly unique per tenant via PostgreSQL constraint `uq_turn_tenant_client_turn_id`.

### 4.2 Concurrency Arbitration Matrix

Under concurrent execution using independent PostgreSQL connections:

| Competing Requests | Scenario                                         | Resolution                                                                                                                                                     | Database Integrity                                   |
| :----------------- | :----------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------- | :--------------------------------------------------- |
| **Req 1 & Req 2**  | Same `clientTurnId`, same payload (Creation)     | Exactly 1 commits `CREATED`; 1 waits for commit and recovers `EXISTING_RECOVERED`.                                                                             | Exactly 1 turn, 2 messages in DB.                    |
| **Req 1 & Req 2**  | Same `clientTurnId`, different payload           | Winning commit succeeds; second request detects payload hash mismatch and throws `DuplicateClientTurnPayloadMismatchError`.                                    | Original turn remains unmodified.                    |
| **Req 1 & Req 2**  | Different `clientTurnId`, same idle conversation | Exactly 1 wins active generation slot; 1 hits PostgreSQL partial unique index `ai_conversation_active_generation_idx` and throws `TurnAlreadyInProgressError`. | Exactly 1 turn committed; zero orphan user messages. |

## 5. Sequence Allocation & Tenant Isolation

### 5.1 Atomic Aggregate Counter Allocation

- `AiConversation.incrementTurnCounter()` and `AiConversation.incrementMessageCounter()` monotonically allocate sequential indexes directly from the root aggregate.
- Eliminates `MAX(sequence) + 1` concurrency race conditions.
- Backed authoritatively by PostgreSQL composite unique constraints:
  - `uq_conversation_turn_index` on `(conversation_id, turn_index)`.
  - `uq_conversation_msg_sequence` on `(conversation_id, sequence_number)`.

### 5.2 Multi-Tenant Boundary Enforcement

- All use cases require `tenantId: string` as their primary scoping argument.
- Every repository query and mutation filters strictly by `tenantId`.
- Cross-tenant requests to non-existent or other-tenant conversations deterministically raise `ConversationNotFoundError(conversationId, tenantId)` with identical error signatures, preventing enumeration or existence probing across tenant boundaries.
